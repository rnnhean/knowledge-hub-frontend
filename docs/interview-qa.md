## 第 43 篇 · 图解 Transformer 架构：大模型底层原理

### 知识点总结

#### 一、大模型的本质：根据上文预测下一个词

Agent 的核心始终围绕 LLM，而 LLM 对开发者来说一直是黑盒。这一节要把这个黑盒拆开。

大模型并不是像人一样真正"理解"世界，而是通过学习海量文本中词与词的搭配规律，学会根据上文预测下一个最可能出现的词。可以把它理解成一个见过无数文章、书籍、对话的"超级补全器"：你说前半句，它根据概率，把后半句最通顺、最合理的内容补出来。我们看到的流畅对话、代码生成、逻辑推理，本质上都是一次次预测"下一个词"的结果。

一句话：**大语言模型就是一个通过海量文本训练出来的"概率预测机器"。**

讲义给了一张两段式对比图：

- **训练阶段（学习词的搭配规律）**：海量文本数据 → LLM → 预测下一个词 → 下一个词的概率分布（例如「的 0.35 / 是 0.18 / 有 0.12 / 在 0.07」）→ 与真实下一个词比较，计算损失、更新模型参数。
- **推理 / 生成阶段（根据上文，预测下一个词，不断重复）**：用户输入上文"今天天气"→ 模型预测下一个词的概率分布（真好 0.42 / 不错 0.21 / 平常 0.10 / 差点 0.08）→ 选择概率最高的"真好"→ 模型再次预测（好 0.40 / 不错 0.28 / 很好 0.20 / 一般 0.05）→ 选"好"→ …… → 生成结果"今天天气，真好，我们"。已生成的词作为新上文，继续预测下一个词，直到结束。

#### 二、Agent 里的 messages 到底是什么

做 Agent 时调用 LLM，会传给模型一组 messages，里面包含：系统提示词（System Prompt）、用户最新提问（User Input）、历史对话上下文（Chat History）、Few-shot 示例（Examples）、工具描述（Tool Schema）、工具调用返回结果（Tool Output）、知识库 / 检索文本（Retrieved Docs）、用户画像 / 长期记忆（User Profile）。

这些内容**全部拼成一段"上文"（Context）**——本质是"给模型的已有已知信息"，LLM 基于所有这些上文，续写下一个 Token 序列，生成回答。

讲义反复强调的核心思想：**LLM 永远在做的事，就是"根据你给的所有上文，预测下一个词"。我们写的 Prompt、历史对话、工具结果，本质上都是在引导它"往正确的方向续写"。**

由此得到两个必须记住的定义：

- **大模型的本质：根据上文，预测下一个词。**
- **Agent 的本质：通过循环，补充上文，引导持续决策。**

Agent 调用工具、检索知识、更新记忆，本质上都是为了让大模型获得更完整、更有效的"上文"，让它的续写方向更准确、更可靠，从而一步步完成复杂的任务。

#### 三、Transformer 的三种架构形态

实现"续写任务"的底层架构就是 Transformer。Transformer 架构主要有三种形态：

| 形态 | 核心机制 | 特点 | 代表模型 | 适用任务 |
|---|---|---|---|---|
| **Encoder-only** 纯编码器 | 双向注意力，只做"理解" | 能同时看上下文前后的内容，做语义理解、特征提取 | BERT、RoBERTa、ES、GTE 等 | 文本分类、嵌入向量（Embedding）、重排序 |
| **Decoder-only** 纯解码器 | 单向掩码注意力，只做"续写 / 生成" | 只能看到已生成的上文，通过"预测下一个词"的方式逐词续写 | GPT 系列、通义千问、Claude、LLaMA、DeepSeek 等 | 文本续写、指令生成、对话交互 |
| **Encoder-Decoder** 组合 | Encoder 理解输入，Decoder 生成输出 | 编码器读原文，解码器输出目标文本，属于"序列到序列"转换 | T5、BART、mBART、PEGASUS 等 | 翻译、摘要等序列到序列任务 |

讲义的结论很明确，做 Agent 只需要记住两条：

- **所有通用对话大模型，全是 Decoder-only 架构。**它的设计天生就是为了"根据上文预测下一个词"，和我们前面讲的大模型本质完全对应。GPT、通义千问、Claude，还有驱动 Agent 运行的大模型，全都是这种架构。
- **我们用的嵌入模型、重排模型都是 Encoder-only 的**，适合做语义理解。

Encoder-Decoder 组合架构在现在的通用对话场景里已经很少用了。

#### 四、双向注意力 vs 单向掩码注意力

这是理解"为什么生成必须用 Decoder"的关键。讲义用两组对比讲清楚：

**（1）在生成任务上**

- 双向注意力（Encoder）：预测「我 爱 自然 语言 **处理**」中的"处理"时，能**直接看到未来的"处理"**——等于作弊，学不会规律，**不适合生成任务**。
- 单向掩码注意力（Decoder）：预测"处理"时**只能看左边，看不到右边**，只能靠上文预测，练得多了就学会规律，**适合生成任务**。

**（2）在理解任务上**

- 双向注意力（Encoder）：句子「小明把钥匙弄丢了，他找了好久，最后在桌子底下找到了**它**。」处理"它"时，能同时看到前后所有词，**立刻知道"它"指的是钥匙**，能完整理解语义，**适合理解任务**。
- 单向掩码注意力（Decoder）：处理"它"时看不到后面的词（后面的词被遮住），**无法立刻确定指代关系**，理解信息不全，**不适合纯理解任务**。

所以 Encoder 架构每一句都是联系全文理解，自然理解得更深刻。嵌入模型根据语义生成向量、重排模型根据相关性打分，这类语义理解类的大模型，都是 Encoder 架构。

**"单向掩码自注意力"也叫因果自注意力。**其中"自"，指计算对象就来自本次输入的文本本身；"因果"，则代表它遵守先后顺序，只能依托上文去推断、续写后面的内容。

#### 五、两大架构的分工

- **Decoder-only**：主打文本生成、对话交互，是 AI Agent 的核心底座。
- **Encoder-only**：主打语义理解、检索匹配，负责结果重排。

两种架构分工明确，共同构成当下大模型应用的底层基础。结合 Agent 流程就能明白：整个 Agent 循环、工具调用、知识库检索、记忆管理，本质都围绕 Decoder 类生成大模型展开；再搭配 Encoder 类嵌入 / 重排模型完成检索环节；二者配合实现完整的智能任务。

#### 六、文本怎么变成模型的输入：五步

Transformer 并不直接处理输入文本，而是先把文本转成 Token。完整五步：

1. **原始文本**：比如"今天天气不错，我们去公园散步吧！"，模型没法直接处理，必须先转换成它能理解的格式。
2. **分词（Tokenizer）**：把句子拆成一个个最小单元，也就是 Token。例：「今 天 天 气 不 错 ， 我 们 去 公 园 散 步 吧 ！」
3. **Token → ID 映射**：每个 Token 对应词表（Vocabulary）里的一个唯一整数 ID。比如"今天天气"对应 **4521**，"不"对应 **1043**。相当于给每个 Token 分配了一个"编号"，方便模型后续查找和计算。
4. **Embedding 查表**：模型通过一个 Embedding 矩阵，把每个 Token 的 ID 转换成一个高维向量表示。这个向量可以理解为 Token 的"语义坐标"，**语义相近的词，向量在空间中的位置也会更接近**，模型就是靠这种向量来理解语义的。
5. **加上位置编码**：**自注意力机制本身不包含位置信息**，模型不知道词的先后顺序，所以需要额外加入位置编码，和 Token Embedding 相加，得到最终的输入向量。

经过这五步，一句普通的文本就变成了一串带位置信息的高维向量序列，这就是 Transformer 模型真正的输入。之后这些向量进入 Encoder 或 Decoder 层，通过注意力机制和前馈网络，一步步完成语义理解或文本生成。

#### 七、从隐藏状态到下一个词：输出投影 + Softmax

每一层 Decoder 处理完，都会输出一组向量，这些就是"隐藏状态"。到了最后一层的隐藏状态，就是模型结合了所有上文、注意力权重后，最终形成的"上下文理解结果"。它本身不是词，也不是概率，只是模型内部的高维"语义向量"。

1. **输出投影（Output Projection）**：把最后一层隐藏状态 h（向量）做**线性变换** `z = Wh + b`，变成每个词的"得分"（logits）。即 `[z1, …, zV]`，对应词表里 the / a / an / … / zebra 各一个得分。含义：**把模型的想法（隐藏状态）翻译成词表里每个词的得分。**
2. **Softmax**：把这组得分变成概率分布，`p_i = e^{z_i} / Σ_j e^{z_j}`，**所有词的概率加起来等于 1**。例：the 0.63、a 0.23、an 0.07、…、zebra 0.01。含义：**把每个词的得分，变成它被选中的概率，我们按这个概率来生成下一个词。**

讲义给的三句话对照很好记：

- 隐藏状态 = 模型的"想法 / 理解"
- 输出投影 = 把"想法"翻译成"每个词的候选得分"
- Softmax = 把"得分"变成"下一个词的概率"

#### 八、自回归生成（Autoregressive Generation）

自回归生成指：在生成序列时，模型在**每个时间步 t 只利用已经生成的内容**（包括输入和之前生成的内容）来预测下一个 token，然后将该 token 追加到序列末尾，继续生成后续内容。

图上演示的逐步过程：

| 步 | 已有上文 | 预测的候选分布 | 生成的 token |
|---|---|---|---|
| t = 1 | 今 天 天 气 很 | 好 / 冷 / 晴 / 热 | 好 |
| t = 2 | 今 天 天 气 很 好 | 合适 / 出去 / 舒服 / 旅游 | 合适 |
| t = 3 | 今 天 天 气 很 好 合 适 | 去 / 在 / 进行 / 来一场 | 去 |
| … | … | … | … |
| t = T | 追加到生成 `<eos>` | — | `<eos>` 结束 |

总结：下一个 token 只依赖之前的 token（满足马尔可夫假设），因此按概率从左到右的链式法则逐步生成序列：

`P(x1, x2, …, xT) = Π P(x_t | x_<t)`

#### 九、两个独立阶段：训练 vs 推理

这套流程会分成两个独立阶段运行。

##### 训练阶段（预训练阶段，模型出厂之前，由大厂完成）

- **训练数据**：海量无标注书籍、网页、对话、代码、论文等纯文本，**不需要人工标注标签**。
- **统一训练任务**：全程都是**下一词预测**。拿完整句子遮住末尾 Token，强制模型仅凭前文预测被遮挡的真实词汇（自监督）。
- **前向计算流程**：和推理的计算路径**完全一致**——文本经过分词、Embedding、位置编码送入多层 Decoder，依靠因果自注意力、前馈网络输出隐藏状态，再经过输出投影、Softmax 得到每个候选 Token 的概率分布。
- **反向更新参数**：模型预测出的 Token 大概率与原文真实 Token 存在偏差，此时通过**损失函数**计算预测值与标准答案的差距，再用**反向传播**算法，迭代更新模型内全部参数。

最终模型在海量数据中自动学到词语语义、语序逻辑、上下文关联、各类行业知识。训练阶段的特点：计算成本极高、需要海量数据、耗时数周至数月、参数持续更新。

##### 推理阶段（生成阶段，开发者调用、Agent 全程运行的阶段）

- **参数状态永为冻结**：模型训练完成后，所有权重固定不变，无论调用多少次接口、运行多少轮 Agent 循环，参数都不会发生任何修改。**模型不会单独记住某个用户的对话，也无法自主学习新知识。**
- **前向计算流程**：Token 编码、多层 Decoder、隐藏状态、输出投影、Softmax 这套计算逻辑和训练完全相同，但**只执行单向前向运算，不再计算损失、不做反向传播更新参数**。
- **自回归循环生成**：模型每次只预测单个 Token，把生成的新词追加到原有上文末尾，拼接出新的完整上下文，再次送入模型重复计算，循环往复直到生成结束符，终止输出。

我们 Agent 里所有历史对话、工具返回内容、检索文档，都会统一拼接进这段输入上文。也正因只做单向前向计算、不保存梯度数据，**推理阶段显存占用更低、响应延迟更小**。做业务开发、搭建 Agent，就是运行在这个阶段。

| | 训练阶段 | 推理阶段 |
|---|---|---|
| 目的 | 学习（更新参数） | 使用（参数冻结） |
| 数据 | 海量无标注文本 | 用户输入 + 拼接的上文 |
| 计算 | 前向 + 反向传播 | 仅前向 |
| 参数 | 持续更新 | 永久冻结 |
| 速度 / 成本 | 慢、贵 | 快、省 |

#### 十、结合 Agent 业务的三条必背要点

讲义在总图里单列了"结合 Agent 业务区分场景"：

1. **为什么 Agent 不能自主学习？** 因为 Agent 全程运行在**推理阶段**，参数冻结，交互内容只影响单次上下文，模型无法修改内部参数，无法真正记住该用户对话。RAG 每次检索都是实时拼接（相当于"开卷"，外部知识）。
2. **为什么 Agent 每条对话都一样快？** 因为推理阶段权重冻结不变，每条请求只做单向前向计算，不像训练时还要反向传播，且所有输入上文进入模型后处理速度基本一致。
3. **Encoder 模型同样区分两个阶段**：训练阶段用双向注意力学习语义关系、海量语料训练；推理阶段做输入向量化、检索打分，用于检索、重排等任务。

#### 十一、全章收束

- 大模型的本质：根据上文，预测下一个词。
- Agent 的本质：通过循环，补充上文，引导持续决策。
- 检索的长期记忆、知识库检索内容、System Prompt、工具调用等，本质都是拼接为上文，让大模型合理续写。
- 完整流程：**原始文本 → 分词 → Token → ID 映射 → Embedding 向量 → 位置编码 → 送入 Transformer → 隐藏状态、输出投影、Softmax 概率换算 → 逐词自回归生成**。
- 两阶段：**预训练阶段**大厂离线完成，基于无标注文本做自监督学习，通过反向传播迭代更新模型全部参数；**推理阶段**（Agent 业务）参数永久冻结，拼接上文逐 Token 生成文本。我们的 Agent 都是在推理阶段修改输入上文，无法修改模型内部参数。

### 预测面试题

**Q1：大模型"理解"语言到底是什么意思？它的本质在做什么？**

**A：** 大模型并不是像人一样真正理解世界，而是从海量文本中学到了词与词之间的搭配规律，本质是一个"概率预测机器"。它做的唯一一件事就是：给定所有上文，预测下一个最可能出现的词（Token）。我们感受到的流畅对话、代码生成、逻辑推理，都是一次次"预测下一个词"串联起来的结果。所以常说的"提示词工程"，本质就是去影响这个续写方向。

**Q2：为什么现在的主流对话大模型全都是 Decoder-only？**

**A：** 因为 Decoder-only 用单向掩码（因果）自注意力，只能看左边已生成的上文，看不到右边，这与"根据上文预测下一个词"的生成任务天然一致。而双向注意力在预测当前位置时能直接看到答案，等于作弊，学不会规律，因此不适合生成。所以 GPT、通义千问、Claude、LLaMA、DeepSeek 这些对话模型都是 Decoder-only。

**Q3：Encoder-only 和 Decoder-only 的区别是什么？各自用在哪？**

**A：** Encoder-only 用双向注意力，能同时看到上下文前后内容，只做"理解"不做生成，适合文本分类、Embedding 向量、重排序，代表是 BERT、RoBERTa、GTE。Decoder-only 用单向掩码注意力，只能看已生成的上文，专门做"续写 / 生成"，是当前对话大模型的绝对主流，代表是 GPT、Qwen、Claude。在 RAG + Agent 里，Decoder 负责生成回答，Encoder 负责检索和重排，两者分工配合。

**Q4：Encoder-Decoder 架构现在还用吗？适合什么场景？**

**A：** Encoder-Decoder 是编码器理解输入、解码器生成输出的"序列到序列"结构，代表模型有 T5、BART、mBART、PEGASUS，适合翻译、摘要这类输入输出都是序列的转换任务。但在现在的通用对话场景里已经很少用了，对话和 Agent 基本都走 Decoder-only。做业务选型时，除非是明确的 seq2seq 任务，否则不必考虑它。

**Q5：一句中文从输入到进入 Transformer，中间经过了哪几步？**

**A：** 五步：原始文本 → 分词（Tokenizer 拆成 Token）→ Token 映射成词表里的唯一整数 ID → 通过 Embedding 矩阵查表变成高维语义向量 → 加上位置编码（与 Token Embedding 相加）得到最终输入向量。得到的是一串带位置信息的高维向量序列，再送入 Encoder 或 Decoder 层。

**Q6：为什么一定要加位置编码？不加会怎样？**

**A：** 因为自注意力机制本身不包含任何位置信息，它对输入的每个位置是"无序"聚合的，模型无法知道词的先后顺序。如果不加位置编码，"我打你"和"你打我"在模型看来没有区别。所以要把位置编码加到 Token Embedding 上，让向量携带顺序信息后再送入网络。

**Q7：模型的隐藏状态怎么变成"下一个词"的？**

**A：** 最后一层 Decoder 输出的隐藏状态是模型结合全部上文和注意力权重得到的"上下文理解结果"，它本身既不是词也不是概率，只是一个高维语义向量。先经过输出投影做线性变换 `z = Wh + b`，得到词表里每个词的得分（logits）；再用 Softmax 把得分归一化成概率分布（和为 1，如 the 0.63、a 0.23）；最后按这个概率分布选词。三句话记：隐藏状态是"想法"，输出投影把想法翻译成"每个词的得分"，Softmax 把得分变成"下一个词的概率"。

**Q8：什么是自回归生成？为什么推理时要一遍遍把上文重新送进去？**

**A：** 自回归生成指模型在时间步 t 只利用已经生成的内容来预测下一个 token，然后把新 token 追加到序列末尾，再继续预测下一个，直到生成 `<eos>` 结束符。数学上就是 `P(x1,…,xT) = Π P(x_t | x_<t)`，每个 token 只依赖它之前的 token。所以必须把不断变长的上文重新送入模型，才能保证每个位置都是基于完整上下文做判断。

**Q9：训练阶段和推理阶段的区别是什么？**

**A：** 训练阶段由大厂离线完成，用海量无标注文本做自监督的"下一词预测"，前向算出概率分布后，用损失函数对比真实答案，再通过反向传播迭代更新全部参数；成本极高、耗时数周至数月。推理阶段（开发者调用、Agent 运行的阶段）参数永久冻结，只做单向前向计算，不计算损失、不反向传播，显存占用更低、响应延迟更小。一句话：训练是"学习"，推理是"使用"。

**Q10：为什么 Agent 无法"记住"用户的对话、也不能自主学习？**

**A：** 因为 Agent 全程运行在推理阶段，模型参数是永久冻结的，无论调用多少次接口、跑多少轮 Agent 循环，权重都不会变。所谓"记忆"其实是把历史对话、用户画像、检索文档这些内容拼进上文再送进模型，属于**单次上下文**级别，不进入参数。想让模型学到新知识只能重新训练或微调，而这是另一条链路。

**Q11：为什么 Agent 每轮对话的响应速度差不多？**

**A：** 因为推理阶段权重不变，每次请求都只做单向前向计算，不像训练那样还要反向传播求梯度、更新参数，所以没有额外的重计算开销。所有输入上文进入模型后的处理路径和速度基本一致。当然，上文越长（Token 越多）前向计算量越大，但那是另一个维度的问题，不是"记住历史导致变慢"。

**Q12：在 RAG + Agent 的完整链路里，Decoder 和 Encoder 分别在哪一步？**

**A：** 知识库入库阶段，用 Encoder 类嵌入模型把文档切片转成向量存进向量库；查询阶段，用同一个 Encoder 嵌入模型把用户问题向量化，做相似度检索，再用 Encoder 类重排模型按相关性打分、重排 Top-K。最后把检索到的文档片段和用户问题、历史对话、System Prompt 一起拼成上文，交给 Decoder 类大模型生成回答。Encoder 管"找得准"，Decoder 管"答得好"。

### 易错点 / 追问

1. **"双向注意力不适合生成"容易被说反。** 面试官会追问：为什么双向就是不合适？答：预测当前位置时能直接看到未来的真实答案，等于开卷考试，训练时它学不到"从前面推后面"的规律；而单向掩码把右边遮住，模型只能靠上文推断，才能真正学到语言规律。反过来，在"它指代钥匙"这种理解任务上，双向能看到后文，理解才完整，单向反而信息不全。

2. **"在线学习 / 记住用户"是高频陷阱。** 很多人会说 Agent 会"越用越懂你"。正确说法：参数在推理阶段永久冻结，Agent 的"记忆"是外部存储 + 拼进上文，属于 RAG / 上下文工程，不是模型在学习。追问还可能继续问：那微调算不算？算，但微调是训练阶段的另一条链路，不是 Agent 运行时发生的。

3. **训练和推理的"前向计算完全一样"要能讲清差别在哪。** 差别只在：推理不做损失计算、不做反向传播、不保存梯度，因此显存占用更低、延迟更小。前向路径（分词 → Embedding → 位置编码 → 多层 Decoder → 隐藏状态 → 输出投影 → Softmax）完全一致。

4. **位置编码的位置容易被忽略。** 常见追问：既然有自注意力，为什么还需要位置编码？答：自注意力本身无序，位置信息必须显式注入，且是和 Token Embedding **相加**后一起送入网络的。

5. **Encoder-Decoder 别答成"已经淘汰"。** 准确说法是"在通用对话场景已经很少用了"，翻译、摘要等序列到序列任务它仍然是标准选择（T5、BART、mBART、PEGASUS）。同时注意区分：Embedding / 重排模型是 Encoder-only，不是 Encoder-Decoder。

## 第 44 篇 · 大模型训练、推理全流程详细图解

### 知识点总结

#### 一、全局框架：先分清 Encoder 和 Decoder

- **Encoder 架构**：用**双向自注意力**，每个位置能同时看到左右两边，因此适合"理解"。典型应用是嵌入（Embedding）模型和**重排（Rerank）模型**，代表模型 BERT、RoBERTa、ES、BGE。
- **Decoder 架构**：用**单向 / 因果自注意力**，只能看左边、不能看右边，因此适合"生成"。代表模型是 GPT 系列、LLaMA、Qwen。
- **结论**：市面上的大模型（LLM）**全部是 Decoder 架构**；嵌入、重排这类模型才是 Encoder 架构。

（讲义给的总图分四块：Encoder 架构、Decoder 架构、训练阶段、推理阶段。训练阶段是"学习参数"——给模型文本、算预测与真值的差别、反向传误差、更新参数；推理阶段是"使用模型"——用户输入进模型、逐步生成输出、**不再更新参数，只做前向计算，所以速度快**。）

#### 二、自回归生成：每一步只产出一个 token

大模型所有文字输出都靠 **Decoder 自回归**逐字生成。比喻是"小学生写句"：每次只写一个字，写完看一遍已经写完的内容，再决定下一个字。

生成"今天天气真好"的过程：
1. 已生成：`今` → 预测下一个字 → `天`
2. 已生成：`今天` → 预测 → `天`
3. 已生成：`今天天` → 预测 → `气`
4. 以此类推，直到写完。

**关键点**：每一步都会把"已生成的内容"整体重新看一遍；模型对每一个位置都是基于**当前位置之前的全部上下文**来做判断。支撑这套逻辑的底层计算单元就是 **Q、K、V 三组向量**。

#### 三、Q / K / V 各是什么

每个输入的 token（例如「我」「喜欢」「吃」「苹果」「。」）都会独立生成一组配套的 Q、K、V 三个向量，各司其职：

| 向量 | 含义 | 职责 |
|---|---|---|
| **Q（Query 查询）** | 代表当前这个词的**检索诉求**，相当于带着问题去上下文里找关联信息 | 由当前正在处理的词生成，用来向其他位置"提问" |
| **K（Key 键）** | 每个字**自带的语义标签** | 只用来和 Q 计算相似度，判断两段内容的相关程度；**只参与打分环节，打完分就不再参与后续运算** |
| **V（Value 值）** | 承载文字**真实完整的语义内容** | **唯一会被加权融合、最终输出**的信息载体 |

一句话记忆：**Q 是"我想找什么"，K 是"我这里有什么标签"，V 是"我这里到底装了什么内容"**。用 Q 去匹配所有 K 打分，再用分数加权所有 V。

**图书馆找书的例子**：你带着"我想找讲宋朝历史的书"这个**需求（Q）**进馆；每本书书脊上的**标签（K）**告诉你它讲什么主题；你按标签匹配度挑出最相关的几本，真正带回家读的是书里的**正文（V）**。

**讲义给的注意力权重实例**：以「喜欢」这个位置的 Q 去和全部 K 匹配，得到权重 `0.10, 0.30, 0.05, 0.40, 0.05, 0.10`（对应"我/喜欢/吃/苹果/。"等位置），再用这些权重去乘各自的 V 并求和。

#### 四、注意力的三步计算（QKV 自注意力层）

1. **打分**：拿当前位置的 Q，遍历全部文字对应的 K 一一匹配，算出两两之间的相关分数。
2. **归一化**：分数经过（Softmax）归一化处理，得到一组**注意力权重**；色块越深代表对应位置语义相关性越高。
3. **加权求和**：用得到的每个权重分别乘以每一个位置的 V，再把全部加权后的 V 累加求和，得到**融合了整段上下文信息的新向量**，作为当前位置的输出。

两个容易漏的细节：
- **K 只负责匹配打分，只有 V 参与加权求和**（K 打完分就退出）。
- 哪怕某段文字相关性偏低、权重很小，它对应的 V **也会参与计算**，贡献少量上下文信息，**不会直接丢弃任何一段语义**。

所以 QKV 自注意力层的唯一作用是：**聚拢全文所有上下文信息，让当前文字能看懂整段文本里的关联语义，输出一个融合全局信息的新向量**。

#### 五、FFN 前馈网络：把"语义"加工成"能说的话"

注意力融合出来的向量虽然含全局语义，但还需要转换成**符合语法、词汇规律的表达**。这一步交给 FFN：

- 结构是**两层全连接网络**做非线性变换（线性变换 W1 → 非线性激活 ReLU/GELU → 线性变换 W2）。
- 作用类似对聚拢来的上下文做**深度整理**：提炼**词汇搭配、语法逻辑、常识关联**。
- 举例：把"苹果、公司、发布、新产品"整理成符合语言习惯的输出；让"苹果"在"公司/产品"语境下不指水果；让"知识"类内容更贴近常识与专业表达。
- 结果：输出向量既保留语义信息，又**更符合语法**，具备完整的语言表达能力。

#### 六、线性输出层 + Softmax：从一个向量到"下一个字"

FFN 之后的向量怎么变成具体的字？

1. **线性输出层**：把高维语义向量**映射到和词表等长的一维数组**，给词库里每一个可能出现的字打出一个**原始匹配分数（logits）**。这一步的分数**没有归一化，不代表概率**。
2. **Softmax 归一化**：把上一步全部字的原始分数转成 **0~1 之间、总和为 1** 的概率分布。
3. **采样 / 选择**：按策略挑出一个 token 作为本轮输出（贪心就是直接取概率最高那个）。

讲义给的例子：概率表 `的 0.02 / 是 0.01 / 在 0.03 / 了 0.35 / 银 0.01`，取最高的「了」输出。

**生活化类比（作者在等下一个词）**：语义已经想清楚了（FFN 输出）→ 把所有可能的词列出来打分（线性输出）→ 心里给每个词一个概率（Softmax）→ 选概率最高的词（采样/选择）→ 写下来。

#### 七、推理全链路七步（讲义的总图）

| 步骤 | 名称 | 做了什么 |
|---|---|---|
| ① | 输入文本 | 输入一段完整上下文（用户提问、之前的对话），作为模型全部参考素材 |
| ② | Token 拆分 | 模型不认识汉字/词语，先把整段文本切成最小计算单元 Token（可以是单字、词语、子词），每个单元独立参与运算 |
| ③ | 词向量嵌入 | 每个 Token 映射成一串**高维数字向量**。文字本身没法被电脑计算，向量是文字数字化的载体，是所有运算的基础 |
| ④ | QKV 自注意力层 | 每个 Token 的原始向量经三组独立权重分别变换出 Q、K、V；用 Q 和全部 K 打分，Softmax 归一成权重，再加权融合全部 V，输出融合全局信息的新向量 |
| ⑤ | FFN 前馈网络 | 两层全连接做非线性变换，深度整理上下文，提炼搭配、语法、常识 |
| ⑥ | 线性输出层 | 把高维语义向量映射到词表大小的向量，给每个候选字打原始分（未归一化，不是概率） |
| ⑦ | Softmax 采样 | 把原始分归一成概率分布，再用贪心 / Top-P 等规则挑出下一个 Token |

然后把这个新 Token 追加到上下文末尾，进入下一轮，**循环直到生成完整答案**。

#### 八、KV Cache：推理加速的关键

**问题**：自回归每输出一个字，如果都把全部历史文本从头完整跑一遍 QKV，会产生**海量重复计算**，推理速度极慢。工业界靠 **KV Cache** 解决这个算力浪费。

**做法**：
- **首次处理用户的初始 Prompt 时**，完整走完 QKV 计算，把所有 token 算出的 **K 向量、V 向量存入显存缓存**。
- **后续每一轮只新增 1 个待预测 token**，只计算这个新位置的 **Q**，**不需要重新计算历史文本的 K、V**。
- 计算注意力匹配时，直接**读取缓存里全部历史 K、V** 打分加权；本轮预测出下一个字后，再把新 token 的 K、V **追加写入缓存**。

**核心思想**：历史信息的 K、V 只算一次、存起来；每轮只为新 token 计算 Q；用缓存的 K、V 快速算注意力；生成后把新 K、V 追加到缓存末尾。

**好处**：避免重复计算，大幅提升推理速度、节省算力。

#### 九、为什么 AI 训练/推理必须跑在 GPU 上

自回归生成过程需要**大量的向量、矩阵运算**（QKV 匹配打分、FFN 特征变换、Softmax 归一化全是批量并行计算），这类计算天生适合在 GPU 上跑，**CPU 串行处理速度会慢几百上千倍**。

**CPU vs GPU 对比表（讲义原表）**：

| 对比项 | CPU | GPU |
|---|---|---|
| 核心数量 | 少（几核~几十核） | 多（成千上万个） |
| 擅长任务 | 复杂逻辑、串行任务 | 大规模并行计算（矩阵运算为主） |
| AI 训练速度 | 慢 | 快（通常快数十倍~数百倍） |
| 内存/显存 | 大内存 | 显存较小 |
| 功耗 | 相对较低 | 相对较高 |
| 典型用途 | 数据预处理、模型调度、推理（小模型）等 | 模型训练、推理（大模型）等 |

**生活类比**：CPU 像几位大厨，一次只能做几道菜；GPU 像成千上万名帮手，同时做很多菜。

**结论**：AI 训练这种"计算量大、可并行"的任务，非常适合在 GPU 上跑。**所以 AI 训练、推理都需要大量显卡。**

#### 十、训练阶段：计算损失与反向传播

推理只是在"用"模型，训练才是"学"模型。

- **训练目的**：让模型学会**根据上文预测下一个词**。所以要给它**正确答案**做监督（监督机制）。
- **计算损失**：把模型的输出结果和真实结果做比较，看**差得有多远**（好不好）。
- **反向传播**：把这个差距的信号**从后往前传回去**，告诉模型里的**每一层该怎么调整参数**，才能变得更好。
- **更新参数**：根据收到的信号调整模型里的参数，下次再试。

**五步训练循环**：输入数据 → 模型前向计算得到预测结果 → 计算损失（和真实标准答案对比，差距大＝损失大）→ 反向传播（把"做得不好"的信号从输出层往回传，告诉每层该怎么改）→ 更新参数（调完再试）。

**这是和推理阶段的区别**：推理是生成完就结束；训练要把生成的内容和正确答案对比，**差别大就要反推回去更新参数**。

**学做菜类比**：看菜谱备菜（输入）→ 炒出菜（前向）→ 尝一口和"好吃"的标准比、发现差很多（算损失）→ 想哪一步出了问题（反向传播到各个炒菜动作）→ 下次少放盐、多翻炒（更新参数）→ 不断尝试、总结、调整，成为大厨。

**一句话总结**：
- 计算损失 = **发现差距**
- 反向传播 = **找到原因并告诉每一层该怎么改**
- 更新参数 = **调整自己变得更好**

#### 十一、训练阶段的完整流程（6 步）

讲义给的训练流程图：

1. **数据准备**：收集海量文本数据（书籍、网页、对话、问答等），作为模型学习的"教材"。
2. **数据处理**：把原始数据清洗、去重、分词、切分，变成模型能"吃"的"文字块"（清洗去重 → 分词切词 → 转换成统一格式 → 得到高质量训练数据）。
3. **模型初始化**：搭建模型架构（比如 Transformer），并随机初始化参数，相当于一个刚出生的婴儿（随机初始化参数）。
4. **训练学习**：让模型在数据上不断学习，预测下一个词（和标准答案对比），并调整参数（更新参数改善预测）。
5. **评估验证**：在独立验证集上测试模型表现，确认它真的学会了，而不只是死记硬背（评估指标：准确率/困惑度；表现好→继续，表现差→返回调整，防止过拟合→早停/增大数据）。
6. **保存模型**：把训练好的模型参数保存下来，用于后续推理应用，部署到服务器/封装成API/用于产品。

**注意：训练是一个反复迭代的过程**——一批数据 → 调整参数 → 再在数据上计算误差 → 效果更好继续调整 → 直到达到目标停止。

**完整闭环**：数据 → 模型 → 推理 → 应用，再回到"收集新数据、学习新案例 → 训练好的大模型 → 理解上下文、生成内容 → 应用落地（问答、写作、代码、创作）"。

#### 十二、训练 vs 推理（讲义对照）

| | 训练阶段（学习规律） | 推理阶段（使用规律） |
|---|---|---|
| 特点 | 需要大量"标注答案"；学会"填空"规则；通过误差反向传播调整参数，提升预测能力 | 不再调整参数；利用已学规律，逐步生成新内容；**自回归循环**，直到结束 |
| 类比 | **学生做作业**（有标准答案、要改错题） | **学生考试/写作**（用已学知识解题，独立完成答卷） |

#### 十三、采样策略：控制"严谨"还是"创意"

拿到下一个 token 的概率分布后，**采样策略直接决定输出内容的严谨度与创意性**。

**1. Greedy 贪心策略（无随机）**
固定选择概率排名第一的字词，**全程不存在随机抽取**，相同输入每次回答完全一致。
- 优势：逻辑精准、无跑偏（输出稳定、可预测性强、逻辑一致性好）。
- 缺点：句式单调、容易重复、单调生硬（缺乏多样性）。
- 适配：代码、专业问答、数据整理等确定性要求高的场景。
- 概率实例：苹果 0.60 / 香蕉 0.20 / 橘子 0.10 / 葡萄 0.05 / 草莓 0.03 / 西瓜 0.02 → 固定取 0.60 的苹果。

**2. Top-K 采样（带随机）**
第一步筛选概率最高的 **K 个**词组成候选池，第二步再在其中采样，在筛选出的词池内按概率随机选词。
- 优势：可控性强，通过 K 值控制多样性，实现简单（相同输入多次运行可选出不同词汇）。
- 缺点：K 值较死板，**K 大随机过强、K 小多样性不足**。
- 适配：在固定候选范围内生成，要求平衡质量与多样性。
- 例子 K=3：只在苹果、香蕉、橘子三个里按概率抽。

**3. Top-P 核采样（带随机，行业主流）**
从最高概率开始**累加数值**，选出**累积概率达到阈值 P** 的所有词作为候选，再在词池内随机采样。
- 优势：**自适应候选词数量**，更符合语言分布，输出更自然，自动增减候选词数量。
- 缺点：P 值过大可能过于随机，过小可能过于保守。
- 适配：候选范围自适应，生成内容更流畅自然。
- 例子 P=0.8：苹果 0.60 + 香蕉 0.20 = 累积 0.80 达标，候选池只有这两个。

**4. Temperature 温度参数（调节随机强弱）**
配套前两种采样使用。**不新增 / 不删减候选词汇**，只**缩放到概率之间的差距**：
- **低温**：放大高概率词优势，随机性大幅减弱，回答保守规整。
- **高温**：抹平概率差距，**冷门词汇更容易被选中**，内容发散、创意更强。
- **温度趋近 0 时，效果近似贪心策略**。

温度实例（同一组词）：
- T=0.3（更确定）：苹果 0.68 / 香蕉 0.18 / 橘子 0.07 / 葡萄 0.03 / 草莓 0.02 / 西瓜 0.01
- T=1.5（更随机）：苹果 0.24 / 香蕉 0.20 / 橘子 0.18 / 葡萄 0.15 / 草莓 0.12 / 西瓜 0.11

**温度梯度直观示例**（从"确定"到"创意"）：T=0 生成"今天吃苹果"；T=0.3 生成"今天天气好，很适合出门"；T=0.7 生成"今天心情不错，去公园散步吧"；T=1.0 生成"生活充满小惊喜，探索未知吧"；T=1.5 生成"宇宙很大，想象力是唯一的边界"。

**小结**：Greedy 无随机最保守 → Top-K 采样可控增加多样性 → Top-P 采样自适应更自然 → 温度调节随机强弱，推荐搭配 **Top-P + 适中温度**使用。

#### 十四、工程落地：OpenAI 系列模型的参数

OpenAI 系列模型支持 `top_p` 和 `temperature` 设置，代码形如：

```js
const model = new ChatGPT({
  temperature: 0,
  topP: 0.5,
  apiKey: process.env.OPENAI_API_KEY,
  configuration: { baseURL: process.env.OPENAI_BASE_URL },
});
```

其中 `topP` 的官方注释是 **"Total probability mass of tokens to consider at each step"**——每一步需要纳入计算的 Token 总概率体量，这正是 Top-P 那条公式在代码里的写法。

**总结**：模型经过前向运算输出全词表的概率分布后，我们就能搭配不同选择策略、温度，来调控随机性强弱，灵活切换严谨问答、创意写作等不同生成风格。

#### 十五、讲义自己给的总结

- 文本被拆分为 Token 并转化为词向量后，生成 **Q 查询向量、K 键向量、V 值向量**。
- 依靠 **Q 与全部 K** 做相似度匹配算出注意力权重，再用权重**加权融合所有 V**，完成全文上下文语义聚合。
- 之后向量送入 **FFN 前馈网络**，进一步提炼语法、常识与词汇搭配特征。
- 再经**线性层**映射至完整词表，通过 **Softmax** 转换为各候选词的概率分布。
- 基于不同的**采样策略**，选词输出。
- 这就是大模型推理阶段自回归生成的全流程；过程中基于 **KV Cache** 缓存 K、V 结果，每次就不用重复计算每个 token 的 K、V 向量了。
- 训练阶段则要给正确答案做监督 → 准备数据集 → 损失计算 → 反向传播更新参数 → 产出训练好的大模型。
- **从数据监督训练，到模型推理生成，构成了一套完整闭环，市面上所有生成式大模型均遵循这套流程。**

### 预测面试题

**Q1：Transformer 里 Q、K、V 分别是什么？为什么需要三个而不是直接用输入向量？**

**A：** 每个 token 经过三组**独立的可学习权重矩阵**，分别变换出 Q（Query 查询）、K（Key 键）、V（Value 值）三组向量。Q 代表"我当前想找什么信息"，K 是每个位置自带的"语义标签"，用来和 Q 算相似度打分，V 是承载真实语义内容、**唯一会被加权融合输出**的载体。分成三路的意义在于把"检索"和"内容"解耦：同一个 token 在"当提问方"和"当被检索方"时需要的表示本来就不一样，用一套向量无法同时兼顾。生活类比是图书馆：Q 是你带着的问题，K 是书脊标签，V 是书的正文。

**Q2：注意力机制的计算步骤是什么？为什么最后用的是加权 V 而不是加权 K？**

**A：** 三步：①拿当前位置的 Q 和全部位置的 K 做相似度匹配，得到分数；②分数做 Softmax 归一化，得到一组注意力权重；③用每个权重乘以对应位置的 V，全部相加，得到融合全局上下文的新向量。用 V 不用 K，是因为 **K 的定位只是"标签"，只参与打分环节，打完分就不再参与后续运算**，它不含要传递的内容；而 V 才是"真实完整的语义内容"。如果拿 K 加权，等于拿目录当正文。另外要强调：即使某段文字相关性很低、权重很小，它的 V 也会参与加权贡献少量信息，**不会直接丢弃任何一段语义**。

**Q3：QKV 之后为什么还需要 FFN？它解决了什么问题？**

**A：** 注意力层的输出是"融合了全局上下文语义"的向量，但它只是把相关信息聚拢起来，**不一定符合语法和语言习惯**，不一定能直接对应到某个词。FFN 是两层全连接网络，中间夹非线性激活（ReLU / GELU），作用是对这个向量做**深度加工**：提炼词汇搭配、语法逻辑、常识关联。比如在"苹果、公司、发布、新产品"的语境下，让"苹果"指向品牌而不是水果。经过 FFN 之后，向量既有语义信息又符合语法，才适合送去线性层映射词表。

**Q4：从"模型算完"到"输出一个字"，中间发生了什么？logits 和概率有什么区别？**

**A：** 线性输出层把 FFN 输出的高维向量映射到**和词表等长的一维数组**，给词表里每个可能的 token 打出一个原始分数，这就是 **logits**。logits **没有归一化，不代表概率**，可正可负、不满足和为 1。然后 Softmax 把所有 logits 转成 0~1 之间、总和为 1 的概率分布，才成为真正的概率。讲义例子里 `了` 的分数最高（0.35），就直接输出「了」。区分这两步的意义在于：**采样策略作用在概率分布上，温度也是先改 logits 再 Softmax**。

**Q5：什么是 KV Cache？它为什么能大幅加速推理？**

**A：** 自回归推理每生成一个 token 都要和全部历史做注意力。如果没有缓存，每轮都要把整段历史文本重新跑一遍 QKV，重复计算量随序列长度爆炸。KV Cache 的做法是：**首次处理初始 Prompt 时完整算一遍，把每个 token 的 K、V 存进显存**；之后每轮只为**新来的那一个 token** 算 Q，直接读缓存里全部历史 K、V 做打分加权；预测出下一个 token 后，再把它的 K、V 追加进缓存。省掉的是历史部分 K、V 的重复投影计算，因此推理速度大幅提升。本质是把"每步 O(n) 的重算"变成"每步 O(1) 的增量计算 + 一次读取"。

**Q6：KV Cache 为什么不缓存 Q？**

**A：** 因为 **Q 是一次性的**。每个位置在**自己作为"当前待预测位置"**时，才需要拿它的 Q 去和历史 K 打分；一旦这个 token 生成完毕，它之后只可能作为"被检索的历史"出现，也就是只贡献 K 和 V。之后的每一轮，新的当前位置会有自己的 Q。所以缓存 Q 没有任何复用价值，缓存 K、V 才是有效的。

**Q7：训练阶段和推理阶段的区别是什么？**

**A：** 训练阶段是"学习规律"：需要**带标准答案的数据集**，模型前向算出预测后要和正确答案比对算损失，再把误差**反向传播**回去更新每一层的参数，是一个反复迭代的过程，目的是让模型学会"根据上文预测下一个词"的规则。推理阶段是"使用规律"：**不再更新任何参数**，只做前向计算，用已经学到的规律自回归地一步步生成新内容，所以速度快得多。类比就是学生做作业（有答案、要改错题）和考试写作（用已学知识独立答卷）。

**Q8：计算损失、反向传播、更新参数分别是在干什么？**

**A：** 三件事一句话概括：**计算损失＝发现差距**，把模型输出和真实结果比较，看差得有多远、好不好；**反向传播＝找到原因并告诉每一层该怎么改**，把"做得不好"的信号从输出层逐层往回传，算出每一层参数该往哪个方向调；**更新参数＝调整自己变得更好**，根据这个信号实际修改参数，下一轮再试。三者串起来就是训练的核心循环：输入 → 前向预测 → 算损失 → 反向传播 → 更新参数，不断重复，模型就越来越好。学做菜的类比：炒出来尝一口跟标准比（损失）→ 回想哪一步出了问题（反向传播）→ 下次少放盐多翻炒（更新参数）。

**Q9：为什么大模型训练和推理一定要用 GPU？**

**A：** 因为大模型的计算主体是**海量矩阵/向量运算**——QKV 匹配打分、FFN 特征变换、Softmax 归一化，本质上都是可批量并行的乘加运算。GPU 有**成千上万个计算核心**，天生适合大规模并行；CPU 只有几核到几十核，强在复杂逻辑和串行任务。所以同样一次训练，CPU 串行处理会慢几百上千倍（讲义表格里 GPU 训练通常快数十倍到数百倍）。代价是 GPU 显存较小、功耗更高；CPU 内存大、功耗低，适合数据预处理、模型调度和小模型推理。用一句话概括权衡：**计算量大且可并行的任务交给 GPU，逻辑复杂、串行的任务留给 CPU**。

**Q10：Greedy、Top-K、Top-P 三种采样策略有什么区别？各自适合什么场景？**

**A：** Greedy 每步直接取概率最高的那个词，**完全无随机**，相同输入每次输出完全一致——优点是稳定、可预测、逻辑精准，缺点是句式单调、容易重复；适合代码生成、专业问答、数据整理这类确定性要求高的场景。Top-K 先取概率最高的 **K 个**词做候选池，池内按概率随机采样，可控但 **K 值死板**：K 大随机过强，K 小多样性不足。Top-P 从高到低**累加概率**，取累积达到阈值 P 的前若干个词做候选（比如 P=0.8，苹果 0.60 + 香蕉 0.20 就凑够了），候选数量**随分布自适应**，更符合语言分布、生成更自然，是行业主流。一句话：Greedy 最保守，Top-K 可控地增加多样性，Top-P 自适应更自然。

**Q11：Temperature 到底在改什么？为什么说温度趋近 0 就近似贪心？**

**A：** Temperature **不新增也不删减候选词**，它只**缩放概率之间的差距**：低温时高概率词的优势被放大，分布更尖锐，随机性大幅减弱，回答保守规整；高温时概率差距被抹平，分布更平缓，冷门词更容易被选中，内容发散、创意更强。当温度趋近 0 时，分布会尖锐到几乎只有最高概率那个词有份额，所以效果近似于贪心策略。实际数据可以看出来：同一组词在 T=0.3 时是 0.68 / 0.18 / 0.07 / 0.03 / 0.02 / 0.01，到 T=1.5 就摊成 0.24 / 0.20 / 0.18 / 0.15 / 0.12 / 0.11。工程上通常**温度控制随机强弱、Top-P 控制候选范围**，推荐搭配 Top-P + 适中温度使用。

**Q12：如果让你设计一个"回答要准确、不能瞎编"的 Agent，你会怎么组合这些参数？**

**A：** 首先把 **temperature 调到很低甚至 0**，让分布尖锐、只取高概率词，牺牲多样性换确定性；其次用 **top_p 收窄候选池**（比如 0.1~0.3 这种小值），把长尾的冷门词排除在外，避免偶发抽到离谱的词；或者干脆用 **Greedy** 保证同输入同输出，方便回归测试和线上复现。反过来，如果是创意写作、头脑风暴这类任务，就提高温度、放宽 top_p。但要清楚一点：**这些参数只能约束"选词随机性"，不能让模型知道什么是事实**——降低随机性可以减少跑偏，不能消除幻觉。真正抗幻觉还得靠检索增强（RAG）、工具调用和输出校验这些外部手段。

### 易错点 / 追问

**1. "K 打完分就不用了"——但缓存里存的恰恰是 K 和 V。**
容易自相矛盾：注意力计算里 K 只负责打分、不参与加权求和，但这**不等于 K 没用**。恰恰相反，KV Cache 缓存的就是每个 token 的 K 和 V，因为下一轮别的 token 还要拿它当"被检索的历史"来打分。面试官常追一句"那到底缓存 K 还是 V"，答案是**两个都要**，只有 Q 不需要。

**2. 线性输出层的分数不是概率。**
很多人把 logits 和概率混为一谈。要能明确说出：线性层输出的是**词表等长、未归一化**的原始分数，可正可负、总和不为 1；只有过了 Softmax 才是 0~1、和为 1 的概率分布。温度也是在 **Softmax 之前**作用在 logits 上的。

**3. Top-K 和 Top-P 的"阈值"含义不是一回事。**
Top-K 的 K 是**个数**（取前 K 个候选词），是硬切；Top-P 的 P 是**累积概率质量**（从高到低累加到 P 为止），是自适应的软切。P=0.8 时如果第一个词就是 0.85，候选池就只剩一个词。面试官常用"P 设成 1 会怎样"来考：候选池等于全词表，等于不做截断，退化成纯按概率随机采样。

**4. 温度和 top_p 都能"调随机性"，但作用机制不同，别混为一谈。**
温度是**改变分布形状**（缩放所有 logits，重新分配概率质量，候选词一个不增不减），top_p 是**改变候选范围**（截断长尾）。所以"低温 + 小 top_p"是双重收紧，"高温 + 大 top_p"是双重放开，两者是正交的两个旋钮。另外温度趋近 0 时近似贪心，此时 top_p 设多少基本没影响。

**5. KV Cache 的复用有严格的前缀约束（文末读者补充）。**
讲义正文讲了缓存怎么存、怎么追加，但没展开一个关键工程约束：**KV Cache 的复用是严格基于前缀（Prefix）的**，两次请求必须从第一个 token 开始就完全一致才能复用；一旦文本中出现任何一个字符的差异，**从该字符位置开始往后的所有缓存全部失效**。这也解释了为什么按前缀命中的 context caching 能打到一折的价格——命中的部分不用重算。反过来，如果每轮请求都在最前面塞了变化的内容（比如把时间戳放在 system prompt 最前面），缓存就一次都命中不了。这个点是 KV Cache 从原理走向工程时最容易踩的坑。

#### 7. 第七份：医保智能数据分析 Agent（Text-to-SQL）

- 周期：2025.09–2026.04（7 个月）。
- 技术栈：Python、FastAPI、LangGraph、Milvus、Neo4j、BGE-M3、Oracle / MySQL、Qwen2.5-32B-Instruct(Q8)、vLLM、SSE、openpyxl。
- 项目描述：基于 LangGraph 的医保结算数据自然语言查询系统。用户输入中文问题（如「按月统计各定点医疗机构费用排名」），系统通过 RAG + Neo4j Schema 知识图谱动态检索相关表字段，自动生成 SQL、执行查询、绘制图表、生成分析报告；兼容 Oracle/MySQL 双库，SSE 实时输出执行进度，支持 Excel 模板导入。
- 核心职责：
  1. **Schema Linking 升级（向量 + 图谱双路）**：Milvus + BGE-M3 稠密/稀疏向量 RRF 融合检索做字段语义匹配；引入 Neo4j Schema 知识图谱（表节点 + 外键/业务关联边），向量定位起始表后沿图遍历自动扩展关联表，解决多表 JOIN 下表关系遗漏导致的 SQL 字段缺失。向量化五要素：**表注释 + 表名 + 字段注释 + 字段名 + 字典值**。
  2. **LangGraph 智能体工作流**：**7 节点状态机**：意图识别 → RAG + SQL 生成 → 执行 → 修正 → 图表 → 分析 → 报告；SQL 校验失败携带错误包让模型自动修正（**最多 3 轮**），执行失败重试（**最多 2 轮**，第 2 轮升级提示词加入检查清单）。
  3. **提示词工程 + 方言适配层**：通用模板（Few-shot、安全校验、字段存在性校验、Oracle/MySQL 方言适配、正反例对比）；Oracle/MySQL 方言补丁（分页、日期函数、字符串拼接、空值排序差异），新增数据库只需加一个方言补丁，核心逻辑不动。
  4. **SQL 生成后三级校验**：语法校验（括号匹配、ROUND 嵌套、LAG 非法语法拦截）→ 字段存在性校验（提取 SQL 引用字段与 Prompt 注入字段交叉比对，幻觉字段直接拦截并反馈可用字段列表触发重试）→ 安全校验（白名单仅允许 SELECT/WITH，拦截 DDL/DML）。
  5. **Matplotlib 自适应图表**：按查询关键词选图（趋势/环比 → 折线图，占比/分布 → 饼图，其余默认柱状图）；标签列用评分算法选择（名称字段优先、编码字段降权），避免 x 轴显示无意义数字代码。
  6. **Excel 模板识别查询 + SSE 流式推送**：上传 Excel 报表模板，自动解析表头推断维度/指标列，中文列名反向映射为数据库字段名，生成结构化描述交给大模型生成 SQL；每个节点完成后 SSE 推进步骤状态，前端逐步渲染。
- 项目成果：**SQL 执行准确率 ≥75%**（**50 条内部测试集**，含自动修正，Oracle/MySQL 双库验证）。
- 作者点评：用 Neo4j 存表和表的关联关系是亮点——先向量检索起始表，再通过图谱查询关联表，最后生成 SQL，技术方案不错；但简历**写得太细，看起来比较累**，简历应简洁清晰、突出重点亮点。

#### 10. 第十份：智能问答与办事督办（Any2Any 多模态检索）

- 周期：2025.11–2026.01（2 个月）。
- 技术架构：LangGraph、Milvus、Dots OCR、RAGAS、Qwen3-VL、zhipuai。
- 背景：政策文件繁多、更新快，RAG 解决「政策理解难」和「知识时效性」；系统要统一理解和检索文本、图像、图文对，支持 Any2Any 跨模态检索（文搜图、图搜文、图文搜图文）。
- 关键做法：
  - **多模态向量**：用 Dots OCR 解析 PDF、Word、HTML；采用私有化部署的 qwen3-VL-7B-Instruct 多模态嵌入模型，把文本与图片映射到同一个向量空间，实现 Any2Any 检索。
  - **文档分块**：章节段落分块 + SemanticChunker 语义切割；图片转 Base64，表格提取为 Table 标签，解决表格或内容跨页断裂。
  - **多路融合**：构建 Dense 和 Sparse 索引，混合检索 + 元数据过滤做多路召回，加权 **RRF** 融合「向量 + 关键词」。
  - **上下文工程**：Redis 存短期上下文，Milvus 存长期上下文；每轮交互后用异步多线程把长期记忆再写入 Milvus 向量库；短期用文本摘要提取，长期用语义 + 全文混合检索，并设距离阈值保证精度。
  - **人机协同**：多次评估都低于配置阈值时，在 interrupt 节点触发中断，人工介入后从中断处恢复工作流。
  - **双层 RAGAS 评估**：第一层对知识库检索出的 doc 评估 **Context Precision + Context Recall**；第二层在输出答案前评估 **Response Relevance + Faithfulness**；每层设阈值，提高响应准确率。
- 作者点评：知识库项目但支持跨模态检索；跨模态是用多模态嵌入把文本、图片存到同一向量空间，**不是 OCR 转文字再作文本语义检索**；检索仍是向量 + 关键词混合；Redis 短期、Milvus 长期，关键词 + 语义混合召回；做了 Agent 评测（召回率、准确率等）。

### 预测面试题

**Q1：医疗问诊项目为什么用 ReAct + Neo4j 知识图谱，而不是纯 Prompt 或固定决策树？**
**A：** 问诊的核心是「下一句问什么」依赖当前症状的鉴别诊断特征，纯靠 LLM 参数内知识容易编造，固定决策树又覆盖不了患者的自由表述。项目把 Neo4j 当外部事实源，ReAct 每轮先查「当前症状 – 并发症 – 鉴别特征」再决定追问，属于「先检索后推理」。图谱还承担实体对齐，把口语映射为标准医学术语，保证检索命中。代价是每轮多一次图查询，要控制跳数和延迟。

**Q2：Mem0 和 Redis 双层记忆怎么分工？30%+ Token 降低是怎么算的？**
**A：** Mem0 管长期事实（过敏史、慢性病、长期用药、既往病史），复诊时按语义向量召回；Redis 管当前会话，滑动窗口裁掉非关键冗余、保留诊疗逻辑链。30%+ 应是对比「原生全量上下文」方案的相对降幅，口径要说明是同一批复诊对话的输入 token 均值还是总量、样本量多少。追问点：裁剪会不会把「无过敏」这类关键否定信息裁掉——正确做法是先把结构化事实写入 Mem0，再裁对话。没有 baseline 和统计口径的百分比在面试里撑不住。

**Q3：既然让 LLM 自主决策，为什么还要 FSM 有限状态机？**
**A：** 医疗场景要求流程可控：症状采集 → 意图识别 → 追问判停 → 诊断输出，节点固定，但节点内「问什么」交给 LLM。判停用两个条件：Top3 预测疾病置信度达标，或用户表达结束意图，避免无限追问或过早下结论。状态机负责「能不能进入下一步」，LLM 负责「这一步怎么问」，职责分离后模型输出漂移也不会跳过采集直接诊断。这也是「Workflow 定流程、Agent 定下一步」的组合用法。

**Q4：工业 RAG-KG 为什么向量、关键词、reranker、知识图谱四样都要？**
**A：** 工业资料既有自然语言，也有型号、故障码、参数名这类强术语，单靠向量对精确符号不敏感，BM25 能兜住术语和长尾；reranker 对多路候选二次排序，保证进入上下文的证据质量。KG 解决多跳：故障码 → 原因 → 处理步骤 → 证据路径，这是相似度检索不擅长的结构化推理。父子分块让子块精准召回、父块补上下文，MinIO 存图表资产以便答案回溯到原文页。权限过滤放在检索阶段，避免无权限文档进入候选集。

**Q5：Agentic RAG 的「自主决策」怎么防止死循环和成本失控？**
**A：** 把循环写成显式状态机：查询改写 → 检索 → 证据质量评估 → 条件重试，评估不过才重试，并设最大轮次和预算上限。质量评估要用可执行判据，比如相关 chunk 数、重排分数、证据覆盖率，而不是让 LLM 自由说「够了」。还要有兜底：证据不足时拒答或转人工，不能无限补采。线上用 LangFuse 记录每轮检索和 token，才能定位成本是哪一步涨上去的。

**Q6：Text-to-SQL 为什么用 Neo4j 存表关系，而不是只把 schema 向量化？**
**A：** 向量检索能定位「起始表」，但多表 JOIN 需要外键和业务关联边，纯相似度容易漏关联表，导致生成 SQL 引用不存在的字段。项目先用 Milvus + BGE-M3 稠密/稀疏 RRF 找到起始表，再沿 Neo4j 的 schema 图遍历扩展关联表，并把「表注释 + 表名 + 字段注释 + 字段名 + 字典值」五要素一起向量化。生成后有语法、字段存在性、安全三级校验，失败携带错误回模型修正，最多 3 轮。SQL 准确率 ≥75% 要主动交代是 50 条内部测试集、含自动修正、双库验证，样本量小不能直接外推。

**Q7：多 Agent 路由的意图识别为什么三路融合？和微调分类器怎么选？**
**A：** 三路是 LLM few-shot、Embedding 相似度、关键词 Pattern：LLM 泛化好但慢且贵，Embedding 快但对细粒度易混，关键词精确但覆盖窄；动态权重让高置信信号主导，低置信度降级到更保守路径。微调分类器适合意图体系稳定、类别多（如 42 类）、QPS 高的场景，延迟低且可控，但需要标注和持续迭代。选择标准是类别是否封闭、数据量、延迟预算、可解释性；也可以级联——分类器先分流，LLM 处理 ambiguous。

**Q8：微调意图识别里 confidence threshold 和 top1-top2 margin 怎么定？**
**A：** threshold 控制「要不要接」，margin 控制「两个意图是不是太接近」，两者结合比单看 softmax 更稳。阈值应在验证集上按业务代价调：路由错的代价高就提高阈值，多放一些到 unknown。unknown 走澄清或转人工，ambiguous 先追问一句再路由，避免硬分。上线后把误判样本回流训练集形成闭环；评估看 Macro-F1 和混淆矩阵，避免大类把 Accuracy 拉高。

**Q9：Human-in-the-Loop 为什么用 LangGraph 的 interrupt + checkpointer？**
**A：** interrupt 在节点内抛出中断，checkpointer 持久化图状态，进程可以退出；人工处理完再用 `Command({ resume })` 从中断点继续，而不是同步阻塞一个请求。退款审批、工单创建这类高风险动作适合这么做，同时要有超时自动拒绝和审计日志。实现上要把待审批摘要写进 state，恢复时只传人工结论，避免重放整条链路。代价是状态存储和并发控制要做对，否则会重复恢复。

**Q10：Any2Any 多模态检索为什么用统一向量空间，而不是 OCR 转文字再检索？**
**A：** OCR 转文字会丢版式和图像语义，文搜图、图搜文这类查询根本无法用纯文本索引完成。项目用 qwen3-VL-7B-Instruct 多模态嵌入，把文本和图片映射到同一向量空间；图片转 Base64、表格转 Table 标签，配合章节段落 + SemanticChunker 分块。检索侧 dense + sparse 混合、加权 RRF 融合并做元数据过滤，Redis 存短期、Milvus 存长期。评估用 RAGAS 双层：检索层看 Context Precision/Recall，生成层看 Response Relevance/Faithfulness。

**Q11：Multi-Agent 异步编排怎么保证任务不丢、上下文不爆？**
**A：** 主 Agent 用 `write_todos` 维护 Pending/Running/Done 状态机并持久化到 Graph State，子 Agent 各自独立上下文、只回传结构化结论，主链路只做编排和汇总。耗时节点并行执行，上下文用摘要压缩，清掉工具调用的中间过程。反思循环用 Generator/Evaluator 子图，达到收敛条件才出片。追问要能对上口径：100 分钟 → 20 分钟是周期缩短 80%、吞吐约 5 倍，与「效率提升 250%」并不是同一个算法，面试时要说清指标定义。

**Q12：线上 RAG 答错，怎么定位是解析、召回、重排还是生成的问题？**
**A：** 先看链路埋点：文档解析有没有丢表格/页眉，query 改写是否偏离，召回 top-k 里有没有正确证据，rerank 后正确证据排第几，最后才看模型是否忠实。可以用 LangFuse 记录每步输入输出，用 RAGAS 的 Context Precision/Recall 判断检索层，用 Faithfulness/Response Relevance 判断生成层。定位后再决定补解析、调分块、换 embedding、加 rerank 还是改 prompt。没有分层指标就只能凭感觉调 prompt，这是最常见的错误。

### 易错点 / 追问

1. **量化指标必须能自证口径。** 讲义里的「诊断逻辑准确率 100%」「SQL 准确率 ≥75%（50 条内部集）」「Token 降 30%+」「满意度 90%+」「100 分钟 → 20 分钟、效率提升 250%」都会被追问样本量、baseline、测量方法；尤其 100→20 分钟与 250% 的换算对不上（周期缩短 80%、吞吐约 5 倍），要能解释指标定义，别把两个口径混着说。
2. **简历不是技术栈清单。** 讲义点名 Text-to-SQL 那份「写得太细，看起来比较累」，第四份「格式不够清晰」；每条亮点应是「解决什么问题 → 怎么做 → 结果指标」，并把每条开头加粗/高亮。堆砌 Qwen、Milvus、Neo4j 而不讲因果，面试官一问「为什么这么选」就露馅。
3. **Agentic RAG / ReAct 要有终止条件。** 只说「让 LLM 自主决定检索」不够，必须能回答重试上限、质量评估判据、证据不足时拒答或转人工；否则就是死循环和成本失控的隐患。
4. **记忆分层别混。** 短期是会话窗口/摘要（Redis），长期是事实与画像（Mem0 / Milvus），两者召回方式不同；只说「用 Redis 做记忆」会被追问长期事实怎么持久化、怎么召回。
5. **评测是区分度，微调不是默认解。** 前两份简历没有评测，第三份的 LLM-as-Judge、第五份的 LangFuse、第十份的 RAGAS 双层评估被作者明确点名为加分项；同时作者也提醒，一般意图识别用 LLM + few-shot 就够，只有类别多、体系稳定、延迟敏感时才考虑微调——不要把微调当万能答案。

#### 1. 第一份：智能客服 Agent（1 年 5 个月，2025.01–2026.06）

5. **多场景路由与人工兜底**：入口 LLM 做意图分类，路由到投诉反馈、政策咨询等链路；**置信度低于阈值或连续两轮未解决**自动转人工坐席，转接时附带对话摘要和已收集信息，方便坐席接手。

#### 2. 第二份：NL2SQL 智能问数系统（11 个月，2025.08–）

**技术栈**：Python、LangChain、LangGraph、RAG、pgvector、PostgreSQL、DeepSeek、Prompt Engineering

**背景**：运营、销售、产品三个部门日常取数严重依赖数据团队，**一个简单查询从提需求到交付往返 1–2 天**。目标是让业务人员用自然语言查数，实时生成并执行 SQL，返回文字解读。

5. **SQL 安全校验与执行体系**：基于 sqlparse 做语法解析 + 自研规则校验，实现**语句类型白名单、表名白名单、JOIN 路径合法性校验**；执行层用**只读数据库账号 + 语句级超时控制 + 强制 LIMIT** 作主防线；复杂查询走 EXPLAIN 预估执行风险。
6. **Prompt 工程与评测驱动优化**：模块化 Prompt 模板体系（系统角色 + 规则约束 + 动态 Schema + Few-shot 样例 + 用户问题）；构建 **200 条评测用例**覆盖单表聚合、多表 JOIN、时间过滤、TopN 等场景，每轮 Prompt 调整后回归跑分、追踪准确率变化。

**项目成果**：覆盖运营、销售、产品 **3 个部门**日常取数；SQL 生成准确率 **89%**；平均响应 **15 秒**；取数流程从 1–2 天缩短至**分钟级**；业务自助取数比例从 **5% 提升至 60% 以上**。

**讲义点评**：这**不完全是大模型生成 SQL**——大部分靠语义层拼装，少部分走 AI 生成；知识库存表/字段信息，用关键词 + 向量混合检索；LangGraph 做多 Agent；用 sqlparse 判断操作是否在白名单里做预检；Prompt 用模板拆分管理、使用时拼接（系统角色 + 规则约束 + 动态 Schema + Few-shot + 用户问题）。**NL2SQL 也是常见 Agent，但简历里写知识库类 Agent 更好。**

#### 5. 第五份：基于多模态 RAG 的儿科疾病数据库系统（10 个月，2025.03–2026.01）

**要解决的问题**：儿科疾病种类繁杂、患儿年龄段差异大，基层医生存在专业检索效率低、诊疗参考依据不权威、答疑不精准的问题。整合权威诊疗指南、临床路径、疾病百科、用药规范、护理方案，做**向量 RAG + GraphRAG 混合架构**。

**关键设计**

- **数据建模**：dots.OCR 解析权威指南、疾病百科等 PDF 中的文本与图片；**Qwen 多模态嵌入模型把文本与图片映射到统一向量空间，实现跨模态检索**；LLM 对文档分块抽取实体、关系、属性，存 Neo4j，供检索阶段做**多跳推理**。
- **分块策略**：以标题为主导递归分块；超长块用 **SemanticChunker 语义切割**替代固定 token 切分；图片独立分块，保证结构与语义完整。

- **上下文工程**：PostgreSQL 分层管理长短期上下文记忆；每轮交互后**异步**把长期记忆持久化到向量库；**短期记忆用文本摘要控制长度，长期记忆用语义 + 全文混合检索并设 distance 阈值**保证精确度。
- **双层 RAG 评估机制**：用 RAGAS 建两层评估——第一层对检索结果评 **Context Precision / Context Recall**；第二层在生成答案之前用 **ResponseRelevancy / Faithfulness** 再评一次；每层设阈值，**多次评估都不达标则触发人工介入审核**。

**讲义点评**：语义 + 关键词 + 知识图谱的混合检索，算 **GraphRAG**；多模态嵌入做跨模态检索时，**直接统一映射比"OCR 抽文字再走文本检索"更靠谱**——OCR 会丢掉图片的布局信息，且图片里没文字时 OCR 直接失效。记忆的做法是"短期滑动窗口 + 摘要，长期语义 + 全文检索，记忆基本都这么搞"。这个项目整体写得好，做跨模态检索 / 图谱推理 / 混合检索的知识库都可以参考。

**讲义点评**：这是知识库项目，切分用了父子分块，关键词 + 向量混合检索，通用搜索通过 **MCP** 接入（百度地图导航链接的生成也是走 MCP）。

#### 7. 第七份：保险业务知识库检索平台（1 年 7 个月，2024.09–2026.04）

**场景**：面向核保、理赔、风控。覆盖保险条款、核保手册、理赔规则、监管文件、体检报告、事故照片等非结构化资料，目标是把散在文档、图片、系统附件里的知识结构化，让业务人员"能直接问、能查到出处，不用再翻原始文件"。

2. **知识切分策略**：先按目录、标题层级、条款编号做**章节级拆分**，再在章节内按语义完整性和 token 长度二次切分。对跨页表格、长条款、核保规则**保留前后文窗口 + 章节路径 + 页码 + 文档来源**；检索结果**按章节聚合展示**，并满足不同业务条线的**权限过滤**。
3. **Milvus 文本 + 图文混合检索**：文本侧 **bge-m3 + BM25 做 RRF 融合召回、bge-reranker-v2-m3 精排，Top3 召回率 64% → 85%**；后期为支持图片和扫描件，引入 **gme-Qwen2-VL-7B 生成图文统一向量**，按意图分成纯文本 / 多模态两路，多模态侧用 **jina-reranker-m0 重排**、图文理解交给多模态 LLM，**复杂图文 Top3 召回率 81%**。
4. **RAG 问答效果优化**：离线侧建评测集，用 **RAGAS** 对召回相关性、答案忠实度、事实一致性做回归评估，按 Query 改写 / 检索 / 重排 / 生成四个阶段定位低分样本再调策略；在线侧基于 LangGraph 增加 **Query 改写、检索质量判断、补充检索、LLM-as-Judge 自检**，按召回分数、精排分数、答案置信度**分层处理**。**幻觉率 21% → 8%。**

**讲义点评**：这个项目把各种格式的文件统一解析为 Markdown，带原文章节路径、页码、权限信息——检索出来既能**定位到原文**，也能**按权限过滤**；切分策略同样是父子分块；多模态嵌入模型做图文跨模态检索"算是最佳实践，见到好多次了"；查询改写和 RAG 质量评估写得比较完整。

#### 8. 第八份：3D 数字人交互智能体 — Agent 全线（7 个月，2025.09–2026.04）

**定位**：3D 虚拟人多模态交互 + 自适应检索增强生成（**Agentic RAG**）一体的企业级智能对话系统，从多源异构数据清洗到高清真视听互动的全链路闭环。功能包括：3D 多模态视听交互（流式 TTS + 数字人口型毫秒级对齐）、自适应反思对话引擎、异构数据自动治理（Markdown 规范化切片 + 双栏人工校验）、纵深分层记忆（跨会话长期记忆、千人千面）。

4. **Redis + Mem0 分层记忆**：短期记忆用 Redis 维护当前 Session 会话窗口；长期记忆对接 **Mem0** 架构，后台**异步提取跨时序的结构化事实（Facts）**并持久化到 PostgreSQL，会话初始化时**动态注入 System Prompt**。
5. **全链路可观测性闭环**：**LangSmith（研发期图拓扑调优）+ LangFuse（线上监控）**；对 **TTFT（首字延迟）、端到端 Latency、Token 成本**精准监控，自动捕获线上失败 Case 并**转化为本地回归测试集**。

#### 10. 第十份：基于大模型 RAG 的养老护理文档知识库系统（4 个月，2025.04–2025.08）

**背景**：养老护理领域大模型知识不符合企业要求、幻觉率高（**传统方案问答准确率仅 62%**），需构建结合图文系统的 RAG，实现实时知识更新与可验证回答，服务内部护理人员培训与上岗。

**职责**：主导 RAG 系统架构设计（基于 **Qwen-2.5** 的 RAG 全流程，统筹向量库部署、混合检索、动态路由）；核心模块选型与实现（领域知识库构建、检索策略优化、动态路由工作流）；评估体系构建与优化。

**解决方案**

1. **知识库构建**：整合护理规范、操作指南、图文案例，采用"**结构化语义分块 + 父子层级分块**"——
   - 结构化语义分块：按标题层级、段落、操作步骤边界切割，**图文合并为同一块（OCR 提取图片文字）**，**块大小 200–800 字（动态调整），重叠 50 字**；
   - 父子层级分块：父块为章节单元（含上下文），子块为章节内细分条目（如操作步骤），建立**层级索引（父块 ID + 子块 ID）**。
2. **检索基础**：部署**弹性分布式 Milvus 集群（M=30, efConstruction=64）**；混合检索（BM25 + 语义检索），**BM25 参数 k1=1.2、b=0.75**；**动态路由机制**基于 LangGraph，按问题类型（术语解释 / 操作步骤）在语义检索与关键词检索之间选最优路径。
3. **实时知识更新与验证**：支持知识库实时更新（新增护理指南、案例）；**检索结果附带知识来源**（如《福寿康养老护理操作规范 2024 版》第 X 章），实现回答可追溯、可验证。

**项目成果**：问答准确率 **62% → 94%**，幻觉率显著降低；混合检索系统响应时间 **≤ 3000ms**；内部培训效率提升 **30%+**；覆盖养老护理 **10+ 核心场景**；护理团队满意度评分 **4.9/5.0**。

**讲义点评**：父子分块先按章节拆大块、内部再切小块、子块关联父块；图片用 OCR 识别文字放进文档块；这份写得比较细，连 **200–800 字、重叠 50 字**都写了；同样是向量 + 关键词混合检索。

### 预测面试题

**Q1：你的智能客服为什么选 ReAct + LangGraph，而不是单次 Function Calling 或者固定工作流？**
**A：** 客服问题的路径不固定——同一个问题可能要查订单、再查退货政策、再判断能否自助处理，单次 Function Calling 只能调一次工具，覆盖不了。LangGraph 的 StateGraph 把「意图识别 → 任务拆解 → 工具调用 → 结果整合 → 回复生成」显式编排成图，同时保留 ReAct 的自主决策：模型自己决定下一步调哪个工具。显式的图结构也让我能在图层面加条件边，比如置信度不足时回退、连续两轮未解决转人工，这些用裸 ReAct 循环很难稳定控制。代价是图设计复杂、调试成本高，所以我会用对话摘要 + 已收集信息这类可观测中间状态来排障。

**Q2：ReAct 模式会不会死循环？你怎么控制单轮工具调用次数？**
**A：** 会，典型表现是模型反复调同一个工具、或在两个工具间来回跳。我在图层面加了两道闸：一是**最大重试/最大步数**，超过就强制走兜底回复或转人工；二是**条件回退**——工具返回空结果或置信度低于阈值时不再让模型自由发挥，而是按预设分支走。另外把 observation 做截断和结构化，避免长 observation 把上下文挤爆后模型重复决策。转人工时附上对话摘要和已收集信息，保证兜底体验不至于断掉。

**Q3：FAQ 为什么"命中就直出标准答案、不走大模型"？阈值怎么定？**
**A：** 因为 FAQ 是标准问法、答案固定，让大模型改写反而引入幻觉和口径不一致的风险，直出还能压延迟和成本。做法是向量检索加一个高阈值做精确匹配，命中即返回标准答案。阈值不是拍脑袋：我会用一批标注过的 FAQ 样本，扫不同阈值下的准确率-覆盖率曲线，取"误命中可接受"的那个点；同时按咨询频次动态调整——高频问题可以放宽、长尾问题收紧。未命中的才走完整 RAG 链路，这条链路上还有重排和生成。

**Q4：你的 NL2SQL 说"已覆盖指标走确定性 SQL 拼装，零 LLM 调用"，那 LLM 到底还干什么？**
**A：** LLM 负责三件事：一是**意图理解与澄清**（多轮追问、模糊表达）、二是**语义层匹配**（判断用户问的是哪个指标、哪个维度）、三是**未覆盖长尾问题的 SQL 生成**（配 Few-shot 样例）。已覆盖的指标由代码按 YAML 里配置的计算公式、表关联规则直接组装 SQL，完全不经过模型，所以这部分零幻觉。这个设计的好处是可预期、可测试：语义层是确定性代码，改一个指标只改配置；代价是语义层覆盖度要持续维护，长尾问题仍然要兜底。面试里我一般会强调"哪里用模型、哪里不用模型"这条界线。

**Q5：NL2SQL 生成错 SQL 怎么发现和兜底？**
**A：** 分两层。第一层是**规则校验**：sqlparse 解析后做语句类型白名单、表名白名单、JOIN 路径合法性校验，不通过就通过 Conditional Edge 自动回退重试（最多 2 次）。第二层是**执行安全**：只读账号、语句级超时、强制 LIMIT 作主防线，复杂查询先 EXPLAIN 预估风险。结果的正确性还有第三道——针对时间表达式这类高频错误，让 LLM 只输出标准化标签（last_month / last_week），实际日期换算放到应用层用确定性代码做，避开了跨月边界这种模型算不明白的问题。

**Q6：89% 的 SQL 准确率是怎么测出来的？200 条评测集怎么构造？**
**A：** 评测集覆盖单表聚合、多表 JOIN、时间过滤、TopN 等典型场景，每条用例有标准 SQL 和期望结果。判定上不看 SQL 字符串是否一致（写法不同也能等价），而是比对**执行结果**是否一致，必要时人工复核。这套集子不是一次性的：每轮 Prompt 或语义层调整后都回归跑分，追踪准确率变化，避免改一处坏一处。我会主动说清 89% 的口径——是针对这套评测集的、覆盖三个部门常见取数需求的准确率，不是"线上所有问题"。

**Q7：父子分块解决了什么问题？子块命中了怎么保证答案有完整上下文？**
**A：** 纯小块检索召回准但上下文碎，纯大块上下文全但向量被稀释、召回不准。父子分块把两者解耦：子块是细粒度检索单元，做向量化并携带父块元数据入库；父块是完整业务章节，存在关系型库（如 PostgreSQL）里。检索命中子块后，用**父块 ID 回查父块原文**，喂给模型的是完整章节而不是碎片。工程上要注意两点：父块要带章节路径、页码、文档来源，方便溯源和权限过滤；子块切分要沿标题层级和语义边界走，不能硬切在条款中间。

**Q8：混合检索里 BM25 和向量怎么融合？为什么用 RRF 而不是加权求和？**
**A：** 两路各自召回 Top-K 后用 RRF 按**倒数排名**融合，公式只依赖名次不依赖分数，避免了 BM25 分数和余弦相似度量纲不同、没法直接相加的问题。分级策略是另一层优化：首轮只用轻量纯向量检索保响应速度，评估不通过进入重检索阶段才切混合检索并扩大召回量——这样大部分简单问题不付混合检索的成本。融合后一般还要接 rerank 精排，RRF 负责把两路的候选并起来，rerank 负责选出真正相关的那几条。

**Q9：你说的 Agentic RAG，跟普通 RAG 的本质区别是什么？怎么防止死循环？**
**A：** 本质区别是**大模型参与检索过程本身**：普通 RAG 是"检索一次 → 生成"，Agentic RAG 是"检索 → 评估 → 改写 → 重检索 → 生成"的自纠正循环，由模型判断检索结果够不够用。工程上必须有终止条件，我一般设**最大重试次数**；另外评估用 LLM-as-a-Judge 对召回 Chunk 做相关性打分时要设阈值，不能只让模型自由判断"还行"，否则容易反复重试。还有一个隐性成本：多轮重检索会推高延迟和 Token，所以要配合分级检索——先轻后重。

**Q10：RAG 效果提升，你怎么证明是检索变好了而不是模型变好了？指标怎么定义？**
**A：** 把链路拆开分别评：检索侧看 **Context Precision / Context Recall**（或用 RAGAS 直接算），生成侧看 **Faithfulness / ResponseRelevancy**，端到端再看问答准确率和幻觉率。这样一旦指标掉了，能定位到是召回、重排还是生成环节。离线侧建评测集做回归，按 Query 改写、检索、重排、生成四个阶段切分，看是哪一阶段低分。在线侧用 LLM-as-Judge 自检并按置信度分层，同时把线上失败 Case 回收进本地回归集。

**Q11：跨模态检索为什么不直接 OCR 成文本再走文本检索，而要用多模态嵌入？**
**A：** OCR 抽文字会**丢掉图片的布局信息**，而且**图片里没有文字时直接失效**。多模态嵌入模型把文本和图片映射到同一向量空间，天然支持以文搜图、以图搜文、视频搜视频，像扫描件、体检报告、事故照片这类场景必须用它。代价是向量维度高、存储和检索成本上升，且模型选型受限（要支持中文/业务术语）。讲义里多份简历都用了这条路，作者的评价是"做跨模态检索用多模态嵌入算是最佳实践"。

**Q12：线上 Agent 出了"答非所问、幻觉、越权操作"，你按什么顺序排查？**
**A：** 先看**可观测链路**：LangSmith / LangFuse 上的 trace，看这一轮的检索结果、重排分数、工具调用序列和 Token 消耗。幻觉先怀疑检索 ——召回为空、召回到旧版本、或 rerank 把不相关片段排到前面；答非所问先怀疑意图识别误路由；越权操作查工具调用是否绕过了敏感工具的审批节点。定位到环节后再改：召回问题改分块/阈值/查询改写，路由问题改意图分类，越权问题是在图里补强制中断点。最后把这条失败 Case 落进回归集，避免同样的问题再犯。

### 易错点 / 追问

1. **"准确率"必须说清口径。** 讲义里出现的准确率五花八门（FAQ 首次命中解决率 78%、SQL 生成准确率 89%、问答准确率 94.8%→96.5%、检索召回准确率 71%→92%、问答准确率 62%→94%），分母和判定方式完全不同。被追问"怎么测的"时如果答不出数据集、判定标准、样本量，整份简历的可信度就崩了。**准备时给每个数字配一句口径说明。**
2. **不要把所有问题都甩给大模型。** 这份讲义里最有价值的两个设计恰恰是"绕开模型"：FAQ 高阈值命中直出标准答案；NL2SQL 已覆盖指标走确定性 SQL 拼装、零 LLM 调用。面试官很爱追问"这块能不能不用模型"，答"都能用模型"是减分项。
3. **"零幻觉 / 幻觉率降到 X%" 是危险表述。** 简历里出现"幻觉率控制在 1% 以内""幻觉率从 21% 降至 8%"时，一定要能说明幻觉率是怎么标注的（人工抽样？LLM-as-Judge？样本量多少？）。说不清就别写绝对化措辞。
4. **父子分块别只说"分了两层"。** 追问点一定落在：子块怎么跟父块关联（父块 ID）、父块存在哪（关系库）、命中后怎么回查、父块太大塞不下上下文怎么办、跨页表格/跨章节条款怎么切。讲义里给的实践是"子块做向量化、带父块元数据存向量库，用父块 id 去 PostgreSQL 查父块原文"。
5. **同一份简历里指标别自相矛盾。** 比如一边写"响应时间 ≤3000ms"一边写"首字延迟 500ms"、一边写"日均数千次并发"一边没提集群规模，面试官会顺着问压测方法和瓶颈在哪。讲义的写法是每个数字都挂在具体机制上（Milvus 参数 M=30/efConstruction=64、BM25 的 k1=1.2/b=0.75、块 200–800 字重叠 50 字），**参数化的数字比漂亮的结论更抗追问**。
6. **项目时长可以很短，但要有取舍。** 讲义里既有 1 年 7 个月的项目，也有 1 个月的项目（商城 AI 助手）。短周期项目就要讲清"在有限时间里做了什么核心模块、哪些是别人配合的"（如"前端可视化由前端同事配合、数据库权限由 DBA 协助配置"），别把整个系统都揽成自己的。

## 第 47 篇 · Agent 面试题押题精讲：RAG 篇

> 来源：神说有光《Agent 面试题押题精讲：RAG 篇》（2026-08-05）。这份讲义本身就是押题清单，共 9 道高频题，每题「问题 + 参考回答 + 图解 + 补充解释」。RAG 相关面试题是 Agent 面试必问，需要重点准备。

### 知识点总结

#### 1. 说一下 RAG 的流程

RAG 分两个阶段：**离线知识库构建阶段**、**在线问答阶段**。

**离线构建阶段**
1. 对各种格式的文档做解析、清洗、分块（Chunk）。
2. 分块后用嵌入模型生成向量，存入**向量数据库**，用于语义检索。
3. 构建 **BM25 倒排索引**，存入**全文检索数据库**，用于关键词检索。

**在线问答阶段**
1. 对用户问题做 **Query 改写**，换成更适合检索的表达。
2. **混合检索（并行两路）**：
   - 向量检索：根据语义匹配相似内容；
   - 关键词检索（BM25）：根据具体术语、专有名词做精确匹配。
3. 两路结果先**去重**，再用 **RRF 算法**合并排序。
4. 用 **Rerank 重排模型**筛选出与问题最相关的文档片段。
5. 把筛选后的片段放入 prompt，交给大模型生成回答。

**补充：去重的做法**
多路召回会出现同一个文本块同时被向量检索和 BM25 命中的情况，产生重复数据。讲义的做法是**基于 Chunk 唯一 ID（chunk_id）去重**；这要求同一个文本块写入向量库、全文检索库时，绑定相同的 chunk_id。

#### 2. 什么是 RRF 算法

**问题背景：两路分数不可直接比较**
- 向量检索的相似度分数区间一般是 0~1，数值越大语义越匹配；
- BM25 关键词检索得分**没有固定上限**，可能是十几、几十甚至上百。

两者取值范围不同，所以多路召回的两个结果列表**不能直接按原始分数融合**。

**RRF（Reciprocal Rank Fusion，倒数排名融合）**
- 不看原始分数，**只看文本块在各结果列表中的排名**来计算融合分值；
- 公式：`RRF = Σ 1/(k + rank_i)`，其中 rank 为该文档在该检索结果中的排名（从 1 开始），k 为平滑常数（如 60）；
- 可以**有效融合向量语义检索与 BM25 关键词检索两路结果**；
- 融合后再从融合后的列表截取前面部分，用 Rerank 重排模型做深度语义排序。

讲义图解的例子：向量检索给文档 A/B/C 打 0.92/0.78/0.62（排名 1/2/3），BM25 给文档 D/A/E 打 42.7/28.3/17.6（排名 1/2/3）。融合排序后为 A、D、B、E、C，再送 Rerank 重排（取 Top-N 再精排）。

**为什么 RRF 粗融合之后还要 Rerank？**
- 例：向量召回 100 条、BM25 召回 100 条；
- 先基于 chunk_id 去重，再用 RRF 重新排序；
- 从融合后的候选列表**截取 Top50**，送入 Rerank 重排模型。

即：双路召回结果很多，先用 RRF 粗融合收敛，再从列表截取一部分做精排。

#### 3. 你知道 Graph RAG 么

Graph RAG 是在**向量 + 关键词混合检索 RAG 的基础上，引入知识图谱做能力增强**。

**它要解决的局限**：向量检索、BM25 关键词检索只针对文本块做匹配，**缺少实体之间的关联链路**，难以推导出分散在不同文档里的间接关联。

**离线构建阶段**：从文档中**抽取实体、关系，搭建知识图谱**，同时对文本分片构建向量索引与 BM25 索引。

**在线问答阶段**：
- 一方面通过混合检索召回相关文本片段；
- 另一方面**提取 Query 内的实体，在知识图谱中遍历关联链路**，找到分散在不同文档里的隐含信息；
- 把图谱关联信息和检索到的文本内容整合在一起，交给大模型生成答案。

**效果对比**：传统混合检索 RAG「只能匹配片段，难以梳理实体关系链条」；Graph RAG「补齐实体关系与跨文档关联推导能力」。

#### 4. 什么是 Agentic RAG

Agentic RAG 是**引入大模型来自主决策怎么检索**。

- 把混合检索、知识图谱检索、联网搜索等各类检索能力**封装为工具**；
- 收到用户提问后，Agent 理解需求，完成 **Query 改写**，**自主选择调用哪种检索工具**；
- 拿到检索结果后，Agent 会**校验现有信息是否足以充分解答问题**；
- 信息不足时，**优化查询语句，发起新一轮检索**；
- 形成「**规划 → 工具调用 → 结果评估 → 迭代重试**」的闭环，直到搜集到充足信息，再整合上下文输出答案。

图解要点：用户提问 → Agent 理解需求 / 问题改写（Query Rewrite）→ 自主选择检索工具（混合检索 / 知识图谱检索 / 联网搜索 / 其他工具）→ 执行检索 → 结果评估：信息是否足够？（足够：整合上下文并输出答案；不足：优化查询语句，进入下一轮检索）。

#### 5. 你知道父子分块策略么

**定义**：先把长文档切分为**粒度较大的父块**，再在父块内部进一步切分出**更小的子块**。

**存储与关联**
- 子块做向量化，存在向量数据库；**父块不做向量化**，存在其他数据库；
- 子块通过 **parent_id** 与对应父块建立关联。

**分工**
- 子块负责**向量检索**，保障召回的精准度；
- 检索命中子块后，再通过关联关系取出**完整父块**，把父块作为上下文交给大模型生成。

**本质**：把「检索用的分块」和「生成用的分块」**解耦**——子块做检索，父块做生成。

**好处**
- 既发挥小分块检索精准的优势，又解决子块内容碎片化、上下文不全的问题；
- 同时规避大分块直接向量化造成的**召回噪声**，让大模型获取完整连贯的上下文，有效缓解幻觉，提升回答的完整度与准确性。

**补充：什么是「召回噪声」**
长文档**直接向量化**，会导致召回不够精准，容易把无关的文档召回，这就是召回噪声——它**属于检索阶段的概念**（不是生成阶段）。用子块做检索可以缓解这类召回噪声，让检索更精准、定位到真正相关的父块；之后再取出完整父块上下文交给大模型生成。

#### 6. 如何降低大模型的幻觉

可以从**知识层、提示词层、模型层、校验层** 4 个层面处理（讲义称「从检索到校验的全链路降幻觉方法」）。

**知识层**（高质量检索 + 精准召回）
- 接入 RAG 检索机制，保障知识库原始数据准确，合理划分 Chunk；
- 采用**向量检索 + 关键词混合检索**，兼顾语义匹配与关键词精准匹配；
- 用 **Rerank 重排模型**过滤相关度低的文档片段；
- 设置**相似度阈值**，阻止低相似度片段进入上下文；
- 引入 **Agentic RAG 自主评估检索结果**，信息不足时迭代补充检索，保障上下文充足可靠。

**提示词层**（强约束 + 减少主观臆断）
- 通过 Prompt 强约束模型，仅依据给定上下文生成答案，要求答案**标注原文引用**；
- 开启**拒答机制**，无匹配信息时如实回复，**禁止模型编造内容**。

**模型层**（选优模型 + 提升事实可靠性）
- 选用**事实性、稳定性表现更优**的大模型；
- 面向垂直领域，可使用高质量业务数据进行**微调**，让模型更倾向依据外部资料作答。

**校验层**（严格校验 + 拦截修正幻觉）
- 调用大模型对输出结果做**二次事实核查**，比对原始上下文；
- 识别出**无依据、前后矛盾**的内容，进行**拦截、修正**，减少错误输出。

#### 7. RAG 如何做权限过滤

讲义给的做法是**基于 RBAC 模型做检索权限控制**。

1. **文档切片入库时**：chunk **继承父文档的权限配置**，把允许访问的角色、是否公开等权限信息作为**元数据**，**同步存入向量数据库与全文检索库**。
2. **用户检索时**：先获取当前用户的**角色集合**。
3. **检索阶段做过滤**：基于角色元数据做筛选，**只在该用户有权访问的切片范围内**执行语义与关键词匹配。
4. 从源头拦截无权限的文档片段。
5. 之后再做 **Rerank 重排**，选出 Top-K 相关 chunk 交给大模型生成答案。

图解流程：文档切片入库 → 权限继承与标注（chunk 继承父文档权限，元数据含允许角色/是否公开）→ 检索请求（获取当前用户角色集合）→ 权限过滤检索（只有有权访问的 chunk 范围内做语义 + 关键词检索）→ Rerank 与生成（对候选 chunk 重排，选 Top-K 交给大模型生成）。图中标注「无权限片段从源头拦截」。

#### 8. 如何评估 RAG 的效果

评估拆成**检索层、生成层两个维度**。

**第一步：构建测试数据集**
- 搭建贴近真实业务的测试数据集，覆盖**高频问题、边界 case、易混淆的问题**；
- 每个问题都要**提前标注**：标准答案、应该命中的文档、核心 chunk 片段，作为后续评测的依据。

**检索层：看两点**
1. 有效信息能否**成功召回**；
2. 召回的有效信息**排序是否合理**。

量化指标：

| 指标 | 含义 | 讲义示例 |
|---|---|---|
| **Recall@K** 召回率 | Top-K 内是否包含需要的文档，衡量**找得全不全** | Recall@5=0.8，意味着 80% 的测试样本中，回答问题必需的 chunk 落在检索返回的前 5 条结果内 |
| **Precision@K** 精确率 | Top-K 里相关文档占比，衡量**噪声多少** | 返回 5 条结果，只有 2 条真正有用，其余是无关内容，精确率就是 0.4 |
| **MRR** 平均倒数排名 | 衡量正确文档的排序位置，**越靠前分越高** | 正确内容排在第 2 位，就打 1/2 |
| **Hit@K** 命中率 | 相关文档只要出现在 Top-K 即命中，**只看有无，不看位置** | Top-5 内有相关文档，Hit@5=1；否则=0 |

讲义小结：**Recall 保证不漏信息，Precision 减少无效内容，MRR 看排序好不好**。检索层这些指标依赖标注好的标准文档，是**可精确计算的客观指标，不依赖大模型打分**。

**生成层：看两点**
1. **忠实度**：保证回答不瞎编、全部有据可依；
2. **答案相关性、完整性**：对标标准答案，校验回答是否**答得准、答得全**。

指标：

| 指标 | 含义 | 讲义示例 |
|---|---|---|
| **Faithfulness** 忠实度 | 校验输出内容是否全部来源于检索上下文，用来识别模型幻觉 | 资料写 v2 支持批量导入，AI 说成 v3 支持，忠实度就很差，属于幻觉 |
| **Answer Relevancy** 答案相关性 | 回答是否针对用户提问，**不跑题、不答非所问** | 用户问接口报错原因，模型大段讲业务背景，没有回答报错，相关性差 |
| **Answer Completeness** 答案完整性 | 是否覆盖标准答案全部关键要点 | 问题需要返回 3 个配置项，回答只说了 2 个，完整性不足 |
| **Context Utilization** 上下文利用率 | 评估模型对检索回来的上下文信息的**实际利用程度** | 检索结果已包含问题解决方案，但模型依旧输出通用套话，没有使用参考信息 |

这几个生成层指标一般用 **LLM as Judge**（让大模型判断打分），也可以**人工复核**。

**总结**：检索层侧重「信息充分召回 + 合理排序」，生成层侧重「答案准确 + 避免幻觉」，二者共同构成完整的 RAG 效果评估体系。

#### 9. 为什么 Claude Code 不用 RAG 检索代码，而是用 grep

Claude Code **早期尝试过本地向量库 + 嵌入模型的 RAG 方案，后来放弃了**，改用模型自主调用 **grep、glob、read 等工具**的 **Agentic Search**。原因有三：

1. **代码需要的是精确匹配，而不是语义模糊匹配**。自然语言适合向量语义检索；但代码的函数名、类名、变量名、报错字符串本身就是**标识符**，更适合关键词精确查找。
2. **代码库高频变更，RAG 索引很容易过时**。代码库频繁改动，RAG 要持续更新索引，**滞后就会拿到已删除、重构的旧代码**；而 **grep 直接读取磁盘实时文件，结果和源码版本完全同步**。
3. Claude Code 现在是 **Agentic Search**，让大模型自主决策检索过程：决定使用 **grep 做内容关键词检索**，或用 **glob 做文件名匹配**，获取候选文件列表后调用 **read 读取目标文件完整内容**；如果信息不足，自动调整搜索关键词，**循环迭代继续查找**。

图解对比：
- **RAG 检索代码**：代码库 → 向量化/嵌入 → 本地向量库 → 语义检索返回 → 返回结果。「缺点 1：代码需要精确匹配，不是语义模糊匹配；缺点 2：代码高频变更，索引容易过时」。
- **Agentic Search（Claude Code）**：模型决策 → 选择检索手段 → grep/glob 关键词/文件名匹配 → read 读取文件完整内容 → 判断信息是否足够 → 不足则调整查询关键词重新检索。「优势 1：实时读取磁盘，结果与源码同步；优势 2：模型自主，可迭代检索」。

小结：代码检索需要**精确、实时、可迭代**，Claude Code 通过 Agentic Search（grep / glob / read）直接作用于真实的代码库，实现更准确、更及时、更高效的检索体验。

### 预测面试题

**Q1：讲一下 RAG 的完整流程。**
**A：** 分离线构建和在线问答两段。离线阶段做文档解析、清洗、分块，分块后用嵌入模型生成向量存入向量数据库（语义检索），同时构建 BM25 倒排索引入全文检索库（关键词检索）。在线阶段先做 Query 改写，再并行跑向量检索和关键词检索两路，结果去重后经 RRF 融合排序，然后用 Rerank 重排模型精筛，最后把片段塞进 prompt 交给大模型生成答案。

**Q2：为什么要做混合检索，而不是只用向量检索？**
**A：** 向量检索强在语义匹配，但具体术语、专有名词这类需要字面精确命中的场景容易漏。BM25 关键词检索正好补齐这一点，按具体术语和专有名词做精确匹配。两路并行召回覆盖面更广，再经由 RRF 融合和 Rerank 重排收敛为高质量上下文，兼顾语义匹配与关键词精准匹配。

**Q3：两路召回结果怎么合并？为什么不能直接按分数相加？**
**A：** 不能直接相加，因为两个分数不在一个量纲上：向量相似度一般落在 0~1，BM25 得分没有固定上限，可能是十几、几十甚至上百。所以用 RRF（倒数排名融合），它不看原始分数，只看文本块在各自结果列表中的排名，按 `1/(k + rank_i)` 累加得到融合分值，排名越靠前贡献越大。

**Q4：既然后面有 Rerank，为什么还要先用 RRF 粗融合一次？**
**A：** 因为双路召回的量很大，比如向量召 100 条、BM25 召 100 条。先把两路结果基于 chunk_id 去重，再用 RRF 重新排序，然后从融合后的候选列表截取 Top50 送进 Rerank。也就是 RRF 负责把高召回的结果快速收敛成一个有序候选池，Rerank 只在这个小池子里做深度语义精排，成本和效果都更可控。

**Q5：Graph RAG 解决了混合检索 RAG 的什么问题？**
**A：** 传统向量 + BM25 混合检索只针对文本块匹配，缺少实体之间的关联链路，难以推导分散在不同文档里的间接关联。Graph RAG 在离线阶段从文档抽取实体和关系、搭知识图谱，在线阶段除了混合检索召回片段，还提取 Query 中的实体在图上遍历关联链路，把图谱关联信息和文本片段整合后交给大模型，从而补齐「只能匹配片段、无法梳理实体关系链条」的短板。

**Q6：什么是 Agentic RAG？它和普通 RAG 的区别在哪？**
**A：** Agentic RAG 是引入大模型自主决策怎么检索。混合检索、知识图谱检索、联网搜索等能力被封装成工具，Agent 拿到问题后理解需求、改写 Query、自主选择调用哪个工具；拿到结果后校验信息是否足够，不足就优化查询语句再检索一轮，形成「规划 → 工具调用 → 结果评估 → 迭代重试」的闭环，直到信息充分才整合上下文输出。普通 RAG 是一次性固定流水线，Agentic RAG 是带评估和重试的闭环。

**Q7：父子分块策略怎么设计，好处是什么？**
**A：** 先把长文档切成语义较完整的父块，再在父块内部切成更小的子块。子块向量化存向量库，父块不向量化、存其他数据库，两者用 parent_id 关联。检索时用子块，因为小块语义集中、召回精准；命中子块后通过 parent_id 取出完整父块，用父块作为上下文交给大模型生成。本质是把「检索用的分块」和「生成用的分块」解耦，既保住小块的召回精度，又解决小块内容碎片化、上下文不全的问题。

**Q8：什么是召回噪声？父子分块怎么缓解它？**
**A：** 召回噪声是检索阶段的概念：长文档直接整体向量化，向量会被多种主题平均掉，召回不够精准，容易把无关文档也召回来。用子块做检索可以让命中更精准、定位到真正相关的父块，规避大分块直接向量化带来的召回噪声；取出完整父块再交给大模型，上下文完整连贯，还能缓解幻觉。

**Q9：怎么降低大模型的幻觉？**
**A：** 按四层处理。知识层：保障知识库数据准确、合理分块，向量 + 关键词混合检索，Rerank 重排，设相似度阈值拦住低相似片段，必要时用 Agentic RAG 迭代补检索。提示词层：Prompt 强约束只依据上下文作答、要求标注原文引用，开启拒答机制禁止编造。模型层：选事实性和稳定性更好的模型，垂直领域用高质量业务数据微调。校验层：让大模型对输出做二次事实核查，比对原始上下文，拦截并修正无依据、前后矛盾的内容。

**Q10：多租户/企业内部知识库，RAG 怎么保证权限不越界？**
**A：** 用 RBAC 做检索权限控制。文档切片入库时，让 chunk 继承父文档的权限配置，把允许访问的角色、是否公开等作为元数据，同步写入向量库和全文检索库。用户检索时先取当前用户的角色集合，在检索阶段就按角色元数据做过滤，只在该用户有权访问的切片范围内跑语义和关键词匹配，从源头拦截无权限片段，然后再 Rerank 选 Top-K 交给大模型生成。

**Q11：怎么评估一个 RAG 系统的效果？**
**A：** 先建贴近真实业务的测试集，覆盖高频问题、边界 case、易混淆问题，每个问题标注标准答案、应命中文档和核心 chunk。然后分两层评：检索层看有效信息能否召回、排序是否合理，用 Recall@K、Precision@K、MRR、Hit@K，这些是依赖标注文档的客观指标；生成层看忠实度、答案相关性、完整性、上下文利用率，一般用 LLM as Judge 打分或人工复核。

**Q12：为什么 Claude Code 不用 RAG 检索代码，而是用 grep？**
**A：** 三点。一是代码需要精确匹配而非语义模糊匹配，函数名、类名、变量名、报错字符串本身就是标识符，关键词精确查找更合适。二是代码库高频变更，RAG 索引容易滞后，会拿到已删除或重构的旧代码，而 grep 直接读磁盘实时文件，和源码版本完全同步。三是 Claude Code 走的是 Agentic Search：模型自主决定用 grep 做内容匹配、glob 做文件名匹配，再 read 读完整文件，信息不足就调整关键词继续找，可迭代。

### 易错点 / 追问

1. **RRF 的 k 和 rank 容易说反。** 公式是 `Σ 1/(k + rank_i)`，rank 是文档在**该路结果里**的名次（从 1 开始），k 是平滑常数（如 60）。常见错误是拿原始分数去算，或者把两路 rank 直接相加——RRF 的价值恰恰在于**只用排名、不用分数**，因为两路分数不可比。

2. **可能被追问「RRF 之后还要去重吗」。** 讲义给的顺序是：**先基于 chunk_id 去重，再做 RRF 重新排序**。前提是同一个文本块写入向量库和全文检索库时绑定了相同的 chunk_id，否则去重无从谈起。如果答成「先 RRF 再去重」，逻辑上就去不干净了。

3. **召回噪声属于检索阶段，别混进生成层。** 讲义明确写了「它属于检索阶段的概念」。父子分块解决的是「大块向量化召不准」，Rerank 解决的是「候选排序」，二次事实核查才是生成层——四层降幻觉方案里每一层各自管什么，追问很容易问到边界。

4. **父子分块的父块什么时候进入链路。** 留言区就有人追问这个。作者的回答是：父块**作为向量检索的结果**参与 RRF 粗融合和 Rerank 重排，不是只等到生成前才拼接。同时父块**不做向量化**、存在其他数据库，靠 parent_id 关联——这两点常被答混成「父块也向量化、只是不参与排序」。

5. **评估指标别只背名字，要说清「看什么」。** Recall 看找得全不全、Precision 看噪声多少、MRR 看排序位置、Hit 只看有无不看位置；生成层 Faithfulness 看是否瞎编、Answer Relevancy 看是否跑题、Completeness 看是否漏要点、Context Utilization 看检索内容是否真被用上。另外要能说出**检索层是客观可计算指标、不依赖大模型打分，生成层才用 LLM as Judge**，这是最容易被追问的一刀。

6. **可能的加试题：文档小改后要不要整篇重新向量化。** 讲义留言区有人问过，作者没给出完整答案（只回了个「1」，另有读者提到「是不是要上版本管理了」）。回答时可以基于讲义已给的信息拆解：去重/关联依赖稳定的 chunk_id，chunk 又携带父文档的权限元数据，所以增量更新时必须保证「未变 chunk 的 id 与元数据不变、变更 chunk 需重新嵌入、被删除 chunk 要从两个库里同步清理」；但**这部分属于延伸推理，不是讲义原文**，面试时宜说明是工程实践层面的考虑。

#### 1. 第一份：金融文档知识库 RAG 助手（2025.08–2026.01，6 个月）

**项目背景**：债券募集说明书、主体评级报告、财务报告、上市公司公告、产品档案及内部研究材料数量庞大、篇幅长、格式复杂、资料分散。投研人员做条款核验、主体研究和历史材料对比时，需要反复查阅多份文档，信息定位及交叉验证成本高。

**技术栈**：LangChain、LangGraph、Milvus、MinerU、Qwen3-VL、Qwen3-Embedding、MinIO、BM25

**核心模块（原文 7 条）**：

1. **文档解析与智能分块**：MinerU 解析 PDF / PPT 等非结构化文档，识别正文、标题、表格和图片等版面元素，**表格提取为 HTML Table**。设计两阶段分块：先按章节标题做结构化切分并保留标题层级、页码等元数据，再按调优后的 chunkSize 和 overlap 对超长内容递归拆分，减少条款、表格及上下文被错误截断。
2. **图片理解与存储**：Qwen3-VL 结合图片及其上下文生成图片描述，提取财务图表、主体关系图等视觉内容的关键信息；图片上传 MinIO，并把 Markdown 图片标签统一处理为 `![图片描述](图片地址)`，**使图片描述能参与文本检索**，同时保留原始图片的访问和溯源能力。
3. **Dense 与 BM25 混合检索**：Milvus 构建稠密向量与 BM25 稀疏索引，Qwen3-Embedding 处理语义问题走 Dense；Sparse 一路匹配债券代码、条款编号、主体名称、财务指标等精确内容；两路结果融合去重，兼顾语义召回与关键词精确匹配。
4. **查询理解与实体标准化**：基于 LangGraph 构建查询理解工作流，做意图识别、实体抽取、主体简称及债券代码标准化，并生成适合向量检索、关键词检索和元数据过滤的改写查询，降低简称、别名、口语化表达对召回的影响。
5. **多跳检索与跨文档问答**：针对主体研究、财务指标变化、条款对比等复杂问题，把原始问题拆成多个检索步骤，分别从募集说明书、评级报告、财务报告、公告中召回证据，再综合多份材料生成回答，实现跨文档、跨报告期的信息关联。
6. **失败重试与人工审核**：首轮结果不足、实体歧义、材料冲突时，由 LangGraph 自动调整查询表达和过滤条件重新检索；证据不足或置信度低的问题通过 **Interrupt 节点**进入人工审核，避免模型在缺少可靠依据时生成结论。
7. **引用溯源与历史版本比较**：为文档块保留原始文件、章节标题、页码、报告期、版本等元数据，回答时返回引用信息；针对评级变化、条款变化，对不同时间版本的相关章节检索对比。

**作者旁白（页 2）**：
- MinerU 是主流文档解析方案，把 pdf、ppt 解析成 markdown 格式。
- 分块是**先按章节拆分，再在内部按长度递归拆分，合并到 chunk 大小**。

#### 6. RAG 评估指标图解（页 8）

讲师把评测拆成两层：**检索层指标**（客观指标，依赖标注标准文档，不依赖大模型打分）与**生成层指标**（通常由 LLM as Judge 或人工复核）。

**检索层**：

| 指标 | 含义 | 示例 | 一句话 |
|---|---|---|---|
| Recall@K 召回率 | Top-K 内是否包含需要的文档 | Recall@5=0.8 表示 80% 测试样本中答案必需的 chunk 在前 5 条内 | 找得全不全 |
| Precision@K 精确率 | Top-K 里相关文档占比 | 返回 5 条，2 条有用，精确率 0.4 | 噪声多少 |
| MRR 平均倒数排名 | 正确文档排序位置越靠前分数越高 | 正确内容在第 2 位，得 1/2 | 排序好不好 |
| Hit@K 命中率 | 只看相关文档是否出现在 Top-K | Top-5 内有相关文档，Hit@5=1，否则 0 | 有无命中 |

小结：**Recall 保证不漏，Precision 减少噪声，MRR 看排序，Hit 看是否命中。**

**生成层**：

| 指标 | 含义 | 示例 | 一句话 |
|---|---|---|---|
| Faithfulness 忠实度 | 输出是否都来自检索上下文 | 资料写 v2，模型说 v3 = 幻觉 | 是否说对（不幻觉） |
| Answer Relevancy 答案相关性 | 是否回答用户问题、不跑题 | 用户问「如何重置密码」，模型答「重置步骤是……」 | 是否答对（不跑题） |
| Answer Completeness 答案完整性 | 是否覆盖标准答案关键要点 | 标准答案 4 个要点，模型覆盖 3 个（75%） | 是否答全（不遗漏） |
| Context Utilization 上下文利用率 | 是否真正用上了检索到的信息 | 引用 3/5 个检索文档的有效信息（60%） | 是否用对上下文 |

小结：**关注是否说对、答对、答全、用对上下文。** 讲师强调：这里需要构建一个评测集来跑那些指标。

- **端到端流式 RAG 管道与进度感知**：装饰器模式标准化注入进度回调，基于 `Flux.create()` + `publishOn` 实现进度消息与 LLM Token 有序混合 SSE 推送。
- **多级缓存与分布式并发控制**：HashMap → Redis → MySQL 三级缓存加速父分段回源；基于 **Redisson + AOP** 实现 `@DistributedLock` 声明式分布式锁，结合 **SpEL 动态 Key**，保障文档切片与向量化操作的**幂等性**。
- **评测闭环**：搭建 **400+ 测试问题集**，采用 **Ragas 自动化指标评估 + 人工抽检**，形成「指标监控 + 问题发现 + 人工校验 + 策略迭代」的持续优化闭环。

**作者旁白（页 13–14）**：先用大模型做意图识别，走三个分支——
1. **ES 混合检索（向量 + 关键词）**：ES 本身也支持向量、支持全文检索，只用它就能做到混合检索 → 用于报销政策类文档查询；
2. **MySQL 结构化查询，生成 SQL 语句** → 用于业务数据查询，比如假期剩余天数（Text2SQL）；
3. **Neo4j 知识图谱检索，生成 Cypher 语句** → 用于组织架构关系查询（Text2Cypher）。

三条分支分别对应不同场景。文档处理方式和前面一样（MinerU + 图片转描述 + 父子分块），意图识别、query 改写、query 路由、混合检索、Rerank 重排都是常规方案；也做了评测问题集自动跑指标 + 人工抽检打分。

#### 10. 总结：这些简历的共性（页 15）

1. **文档解析基本都是 MinerU**，然后图片用大模型转成图片描述参与检索，源文件上传 MinIO。
2. **父子分块策略**很常见：子分块用于向量精确检索，关联的父分块给大模型生成回答。
3. **引用溯源必做**：保存文档信息时同时保存元数据，比如文件路径、页码、版本等。
4. **SSE 交互协议**很多是自定义事件类型，但比较麻烦也不全，**可以直接用 Vercel AI SDK 的 Data Stream Protocol**。
5. **意图识别**都是 **LLM + Few Shot + CoT** 的方式。
6. **HyDE 假设文档检索**：基于 query 让大模型生成一个符合文档格式的回答用来检索。
7. 和混合检索、网络检索的结果一起 **rerank 重排**，选出最相关的文档生成回答。
8. HyDE「就是召回的角度多了一个而已，和只用混合检索差别不大」。
9. **评测部分要准备一个评测数据集**，具体指标就是上一节讲的那些。
10. 其余如 **Query 改写、混合检索、RRF 粗融合**都是必备的。

### 预测面试题

**Q1：你简历里 RAG 项目的召回率是怎么提升的？**
**A：** 分三层做。第一层是检索侧：稠密向量 + BM25 稀疏向量混合召回，用 RRF 或 Milvus 的 WeightedRanker 融合（例如讲义里语义 0.8 / 关键词 0.2）；再用 BGE-Reranker 交叉编码器精排。第二层是查询侧：Query 改写、实体与型号标准化（把简称、口语映射到规范实体）、支持多轮指代消解。第三层是召回角度扩展：加入 HyDE 假设文档检索、联网搜索等并行链路。我在项目里的实测口径是 Top5 召回率从 82% 提升到 96%。

**Q2：文档切分你是怎么设计的？为什么不用固定长度？**
**A：** 固定长度会把表格、条款、上下文从中间截断，导致回答残缺。我采用的是分层切分：先按章节标题做结构化切分并保留标题层级、页码等元数据，再对超长内容按 chunkSize 和 overlap 递归拆分，最后做短块合并。另一版是按「标题层级切分 + 代码块护栏 + 文本装箱（Bin Packing）+ Token 预算」约束切片长度，保证语义完整、粒度均匀。同时用父子分块：子块小、用于精确向量匹配，命中后回源父块拿完整上下文交给大模型。经测试集验证，召回完整度从约 75% 提到 90% 以上。

**Q3：父子分块具体怎么落地？父块回源的性能问题怎么解决？**
**A：** 子块单独做 embedding 写入向量库，但元数据里保存指向父块的 ID；检索命中子块后，用父块 ID 回源取全文作为 LLM 的上下文。父块回源会带来额外查询压力，所以做了 HashMap → Redis → MySQL 三级缓存，配 30s TTL 和空值缓存防击穿，把回源查询压力降了一个量级。

**Q4：RAG 的评测你是怎么做的？**
**A：** 先构建一个评测集，讲义里是 200+ 条贴近真实业务的 Benchmark，或 400+ 测试问题集。指标分两层。检索层是客观指标、不依赖大模型打分：Recall@K 看找得全不全、Precision@K 看噪声多少、MRR 看排序好不好、Hit@K 看有没有命中。生成层通常交给 LLM as Judge 或人工复核：Faithfulness 看是否来自检索上下文、Answer Relevancy 看是否跑题、Answer Completeness 看是否答全覆盖要点、Context Utilization 看是否真用上了检索信息。Ragas 可以自动化跑这套指标，再配人工抽检形成迭代闭环。

**Q5：PDF 里的表格、公式、扫描件怎么处理？纯文本解析会丢什么？**
**A：** 普通解析器对表格、公式、扫描件基本无能为力，会把版面结构拍平，丢图表信息。我用 MinerU 做深度解析，识别正文、标题、表格和图片等版面元素，表格提取为 HTML Table，输出结构化 Markdown。图片和图表另外走多模态：Qwen3-VL 或 qwen3-vl-flash 结合上下文生成图片描述，原图上传 MinIO，把 Markdown 图片标签统一成 `![图片描述](图片地址)` 这种形式——这样图片描述本身能参与文本检索，同时还能溯源到原图。

**Q6：HyDE 是什么？它真的有用吗？**
**A：** HyDE 是假设文档检索：让 LLM 根据 query 先生成一段符合目标文档格式的假设性回答，用这段回答去做向量检索，再去匹配真实文档。这么做等于多加了一个检索角度，能召回更多文档；但作者的观点是它只是让召回变多，然后再由 Reranker 重排选出真正相关的，效果和「向量 + 关键词混合检索」差别不大。所以在我们架构里它是三路并行中的一路，最终还是要靠 rerank 收口。

**Q7：为什么要 RRF 融合？直接加权分数不行吗？**
**A：** 不同检索链路的分数分布完全不一样——向量余弦相似度、BM25 分数、图谱检索的相关度、网络搜索的打分，量纲和分布都不同，直接加权需要反复调参也不稳。RRF（倒数排名融合）只看排名不看分数，公式是 Σ 1/(k + rank)，天然解耦了不同链路的分数量纲差异，实现简单且稳健。融合完再交给 Reranker 做精排，效果更好。

**Q8：RAG 的幻觉怎么控制？**
**A：** 三个层次。检索侧：保证召回质量，用 rerank + 断层检测动态截断 TopK，把低相关文档剔掉，避免无效上下文误导生成。生成侧：基于 LangGraph 的 Deep QA 节点状态机，校验大模型返回的结构化溯源证据，并做「无来源声明删除」——模型说了但检索材料里没有依据的内容直接删掉，讲义里这个机制让无依据生成的 Bad Case 比例下降了近 30%。兜底侧：证据不足或置信度低时通过 Interrupt 节点进入人工审核，不让模型硬编。

**Q9：引用溯源怎么做的？只存页码够吗？**
**A：** 核心是在分块入库时就把元数据一起存下来：原始文件、章节标题、页码、报告期、版本、权限等。回答时把对应 chunk 的元数据随引用一起返回，前端就能点开定位到原文。只存页码不够——一是跨页的表格和条款会定位不准，二是像评级变化、条款变更这类问题需要按版本做跨期对比，所以版本和报告期也得存。第五份简历里还额外存了权限，因为企业内部文档有访问控制。

**Q10：意图识别怎么做？为什么准确率能到 96% / 98%？**
**A：** 用 LLM 做意图分类 + 结构化实体抽取，输出 JSON。准确率提升主要靠两点工程手段：一是 CoT，让模型先输出思考过程再给结论，复杂逻辑的推理效果明显更好；二是 Few-shot，给少量典型样例锚定输出格式和边界。另外就是结构化输出的容错：用 7 步 JSON 容错修复管道处理 Markdown 包裹、中文引号、尾部逗号这类不规范输出，避免因为解析失败被误判成识别错误。

**Q11：多数据源的路由是怎么设计的？路由错了怎么办？**
**A：** 用 LLM 先做语义分析完成意图路由，把问题分发到三个分支：知识类文档查 ES 混合检索（向量 + 全文），业务数据类查 MySQL 走 Text2SQL，组织关系类查 Neo4j 走 Text2Cypher。三条分支场景很清晰——报销政策查 ES、假期剩余天数查 MySQL、组织架构查 Neo4j。路由判断本身可能出错，所以设计了路由失败自动降级为兜底检索，保证系统鲁棒性。

**Q12：前端流式输出你是怎么接的？会自己定义协议吗？**
**A：** 后端用 SSE 推送。讲义里两种做法：一种自己定义事件类型，比如 4 类 `[PROGRESS]` `[REFERENCE]` `[CARD]` + Token，或 6 种事件类型；用装饰器模式解耦流式回调，把阻塞操作调度到弹性线程池，再用 `Flux.create()` 编排进度消息和 LLM Token 的有序输出。另一种直接用 Vercel AI SDK 的 Data Stream Protocol——作者的看法是自定义协议比较麻烦也不全，Vercel 那套更完善，支持 vue、react 等各种前端框架接入，不用自己解析协议。

### 易错点 / 追问

1. **别把「三路并行」说成串行。** 讲义反复强调三路（混合检索 / HyDE / 联网搜索）是基于 LangGraph 同时启动、无需串行等待，目的是降低整体响应延迟；但融合是**先本地两路 RRF 粗融合去重，再和网络结果一起 rerank**，不是直接三路一起 RRF——这个顺序细节面试官会追问。

2. **HyDE 的作用别夸大。** 作者原话是「就是加了一个假设文档的检索角度，召回文档的更多」「和前面只用向量 + 关键词的混合检索差别不大」。如果说成「HyDE 大幅提升精度」就与讲义口径不符，真正决定精度的是后面的 rerank。

3. **量化指标要能说清口径。** 讲义里出现了多组数字，别混着说：召回完整度 75%→90%+（切分策略，喜之郎）、Top5 召回率 82%→96%（检索与重排，喜之郎）、意图识别 78%→96%（InsightFlow）、意图识别准确率 98%（喜之郎）、Graph RAG 有效召回率提升 18%~25%、Bad Case 下降近 30%、解析与向量化成本降约 40%、WAU 150+ / 30+ 知识空间 / 1.5 万份文档 / 200+ Benchmark / 400+ 测试问题集。被问「这个数怎么来的」要能讲到对照口径（较纯向量基线、经测试集验证）。

4. **SSE 协议不必自己造。** 讲义里好几个项目都自定义了事件类型，但作者明确说这样做「比较麻烦也不全」，可以直接用 Vercel AI SDK 的 Data Stream Protocol。面试时如果只会说自己定义协议，会被追问「为什么不用现成的」。

5. **RAG 简历不是只有互联网公司能做。** 作者的行业观察是：食品公司、制造业、机器人公司都有 Agent 开发岗，三四线城市也有。被问「你们公司没这个业务怎么包装」时，这个视角比硬编一个互联网场景更站得住；但也要注意讲义本身是「简历参考库」，写作时的原则是技术链路真实、量化口径自洽。

## 第 49 篇 · RAG 准确率怎么判断与线上监控

> **本篇不是讲义内容**，来自本项目的真实实现与设计取舍（`knowledge-hub-backend/src/ai/eval/`）。面试时按自己的项目讲，不要当成通用标准答案背。

### 知识点总结

**RAG 的「准」是多维的，必须先拆层，混在一起谈就没法定位问题。**

| 层 | 要回答的问题 | 常用指标 | 能否线上测 |
|---|---|---|---|
| 检索层 | 该找的资料找没找到 | Hit@K、Precision@K、MRR、NDCG | 不能，需要金标 |
| 生成层 | 回答有没有忠于资料 | Faithfulness、Completeness、拒答质量 | 只有忠实度可以 |
| 端到端 | 用户最终有没有得到答案 | 👍/👎、追问率、引用点击率、放弃率 | 能，但都是代理信号 |

**两个必须讲清楚的区分：**

1. **有参考指标 vs 无参考指标**。Hit@K、Completeness 需要标准答案才能算；Faithfulness 只需要「回答 + 检索资料」，所以能搬到线上。
2. **离线评测 vs 线上监控**。离线评测防退化——改 prompt、换模型、调参数后跑一遍；线上监控看真实流量有没有变差。金标集覆盖不到长尾，所以离线全绿不代表线上没问题。

**项目的实际实现**：金标集 + 9 个评测器（意图、工具策略、改写循环、拒答质量、Hit@5、Precision@5、误命中、要点覆盖、忠实度），通过 Langfuse Experiment 跑；`runForEval` 走线上同一个 Agent，保证评测对象和线上一致。

### 预测面试题

**Q1：怎么判断 RAG 出来的东西准不准？**
**A：** 不能用一个数字回答，我拆成三层。第一层检索准不准：准备一套金标集，每个问题标好应该命中的文档，算 Hit@5（期望文档在不在前 5 条）和 Precision@5（前 5 条里有几条相关）——只看 Hit 会漏掉「找到了但夹在一堆垃圾里」的情况。第二层生成准不准：这一层最关键的其实不是答得全不全，而是有没有编。所以用 LLM judge 判忠实度，把回答和本轮检索到的资料一起给它，判断每个制度性断言能不能被资料支撑。第三层端到端：线上没有标准答案，只能看追问率、引用点击率、拒答率、用户反馈这些代理信号。

**Q2：线上没有标准答案，怎么测？**
**A：** 要区分有参考指标和无参考指标。像 Hit@K、要点覆盖这些必须有标准答案，只能离线测；忠实度不需要标准答案，只要「回答 + 检索资料」就能判断，所以线上可以按比例抽样跑。抽样成本要控制，只对本轮有检索结果的回答抽，纯闲聊跳过。

**Q3：LLM 打分靠谱吗？**
**A：** 不完全靠谱，所以要校准。我会定期拿几十条人工标注过的样本，算 judge 和人的一致率；低于 80% 就说明 judge 本身漂了，需要重新校准 prompt 或换模型。不校准的话，你监控的是 judge 的稳定性，不是系统的质量。

**Q4：指标涨了但用户还是不满意，怎么办？**
**A：** 说明指标和业务目标脱节了。这时候要回到用户反馈的样本，逐条看卡在哪一层——是检索没召回，还是召回了但生成没用好，还是资料本身就没有。指标是用来定位问题的，不是用来交差的。

**Q5：离线评测和线上监控是什么关系？**
**A：** 两套分开建。离线是「防退化」：改 prompt、换模型、调检索参数之后必须跑，一次只改一个变量，否则无法归因；线上是「发现恶化」：看真实流量里的代理指标和抽样忠实度。离线保证「没变差」，线上保证「现在不差」。另外我们的纪律是离线评测不进 PR CI——LLM 有随机性，同样的代码跑两次分数就会有波动，把不确定的东西放进 CI，结果是 CI 经常红，然后所有人都开始忽略 CI。

**Q6：评测集要多少条？指标要不要多做几个？**
**A：** 至少要 60 条，再少的话指标波动全是噪声，判断不出改动好坏。指标也不宜贪多：指标越多，越多题目会「跳过」（返回 null），反而看不清整体。另外「不适用」和「0 分」必须分开——不适用的题返回 null 而不是 0，否则平均值会被稀释。跑稳了再按需加指标。

**Q7：你项目里金标是怎么标的？有什么讲究？**
**A：** 金标用文档标题子串而不是 documentId，因为文档 ID 在本地和 CI 环境会变，标题稳定；匹配用双向 includes，避免「差旅」和「差旅费报销制度」对不上。空数组有明确含义——表示「库里确实没有这个制度」，专门用来算误命中率，不能省略。要点覆盖和禁用事实交给 LLM judge，不在金标里堆同义词。

### 易错点 / 追问

1. **别一上来背 RAGAS 的指标名单。** 面试官问「怎么判断准不准」，想听的是你知不知道指标怎么分层、哪一层在线上根本测不了。直接背 Faithfulness / Answer Relevancy / Context Precision 反而像没做过。

2. **别把代理指标当准确率。** 拒答率高可能是因为用户问的本来就超纲。代理指标上线前要用 👎 的样本回测：如果 👎 样本的追问率、空召回率显著高于 👍 样本，这个指标才有区分度。

3. **judge 不校准就是自欺欺人。** LLM-as-judge 会随模型版本、prompt 微调而漂移。被追问「你的 judge 可信吗」，答不出校准方式就是硬伤。

4. **「不适用」和「0 分」不是一回事。** 项目里不适用返回 `value: null`，并且 null 不写入 Langfuse，避免把「跳过」平均成低分。

5. **离线全绿不等于线上没问题。** 金标集是人出的题，覆盖不到真实长尾。这是线上监控存在的唯一理由，被问到「有离线评测了为什么还要线上监控」时要能答出来。

6. **评测对象必须和线上一致。** 如果拿一个「评测专用的简化链路」去测，分数再好看也没有意义。项目里 `runForEval` 走的就是线上同一个 Agent，只是不落会话和记忆。
