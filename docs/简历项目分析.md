## 一、结论先行

读完 109 张图，六批合计并出 **64 条原始项目条目**（批次 1 共 11、批次 2 共 12、批次 3 共 14、批次 4 共 6、批次 5 共 14、批次 6 共 7）；其中约 10 条在不同简历里重复出现（工业 RAG-KG、医保 Text2SQL、儿科多模态 RAG、MCP-Agora、MultiMind、医疗智能问诊等），**去重后约 54 个项目**。

结论只有一句话：

> **这批人在写的，不是"业务系统"，是"给业务系统加一个 Agent 大脑"。**

具体表现为四点：

1. **RAG 几乎是入场券**：六批里 RAG 出现率 60%~92%，没写 RAG 的项目大多写了 GraphRAG 或 Text2SQL。
2. **LangGraph 是事实标准**：批次 1 的 11 个项目里 9 个出现 LangGraph；批次 3 的 13 个里 13 个出现；批次 4 的 6 个里 5 个。
3. **业务域极度分散**：法务、医疗、工业维修、财税、金融、人力、建筑、保险、电商客服、养老、车联网、出版、医美……**没有统一的"热门场景"**。
4. **稀缺的不是业务，是工程细节**：真正拉开差距的是「interrupt + checkpoint 断点恢复」「父子分块 + 三级缓存」「RRF 多路融合」「MCP Server 化」「RAGAS 双层评估」这类东西。

**对你的直接含义**：项目选什么业务不重要，重要的是**它能不能承载上面那套工程细节**，并且**你能在简历上讲出"为什么这么切"**。

## 二、简历里的项目，按形态分成六类

把 54 个去重项目按「AI 在系统里扮演什么角色」归堆，比按业务域归堆更有信息量。

> **先说明口径**：这些类型**不是互斥的**。一个项目经常同时属于 2~3 类（比如「合同风控审查」既是 A 的 RAG 检索，又是 B 的多 Agent 分工，还是 C 的 LangGraph 状态图），所以下面各类数量之和会大于 54。归类按「它最想突出的那一面」算主类。

### 类型 A：RAG 知识问答（主类约 30 个，占比最高）

**形态**：文档入库 → 分块 → 向量化 → 混合检索 → 精排 → LLM 生成 → 带引用输出。

**业务外壳**：企业知识库、法务法规、医疗指南、工业手册、建筑规范、保险理赔、出版社图书、医药 SOP、金融研报、国铁采购规则……

**技术共性（几乎每个项目都有）**：
- 解析：**MinerU** 出现频率极高（批次 2 的 12 个项目里 9 个），其次是 Dots.OCR、PaddleOCR、LlamaIndex SimpleDirectoryReader
- 分块：**父子分块**（子块召回、父块补全）几乎是标配；进阶版是 SemanticChunker、标题层级切分
- 检索：**BM25 + 向量混合召回**，用 **RRF** 融合
- 精排：**BGE-Reranker / Qwen3-Reranker**，用 **ONNX Runtime 进程内加载**（Java 栈的简历特别爱这个，零网络延迟）
- 评估：**RAGAS**，指标是 Context Precision / Context Recall / Faithfulness / Answer Relevancy

**这批里写得最硬的三个**：
- 建工智库（批次 3）：LangGraph 10 节点 + 3 组条件边，四类问题路由（通用/明确/模糊/宽泛）→ HyDE/Multi-Query → 置信度路由 → Top-1 分数低于 0.75 触发联网，全链路有 RAGAS 数值
- 喜之郎员工知识库（批次 1）：三源路由（ES / MySQL Text2SQL / Neo4j Text2Cypher），召回完整度 75%→90%+，Top5 82%→96%，意图准确率 98%
- 保险理赔知识库（批次 2）：Query 改写 4 维策略 + 7 步 JSON 容错修复管道 + HashMap→Redis→MySQL 三级缓存，意图准确率 78%→96%

### 类型 B：多 Agent 编排（主类约 10 个）

**形态**：一个 Orchestrator/Router + 若干专业 Agent，各自有工具集。

**典型分工**：
- 按业务域拆：General / Technical / Billing Agent（MultiMind，两批都出现）
- 按职能拆：调度 Agent / 法律审查 Agent / 商业风险 Agent / 报告 Agent（合同风控）
- 按主从拆：主控 Agent（拆解 + 路由 + 反思 + 重规划）+ 从 Agent（知识检索 / 订单服务）
- 按流水线拆：DocParser / KnowledgeExtract / QA / KnowledgeUpdate（多 Agent 知识库）

**关键技术点**：
- **上下文隔离**：子 Agent 只看自己那部分，防止长周期任务污染主上下文（ERP 采购助手、多 Agent 创作平台都强调这点）
- **Planner-Executor**：Planner 生成最多 5~6 步的受限串行计划，Executor 用 LangGraph 状态机调度（商家经营助手）
- **动态路由 + 局部重规划**：主控 Agent 根据执行轨迹反思，失败时只重跑局部（跨境代购客服）

### 类型 C：Agent 工作流 / 状态机（主类约 8 个）

**形态**：LangGraph StateGraph，显式节点 + 条件边，不是自由 ReAct。

**关键点**：
- 节点数被当成卖点写：「15 节点 22 条边」（AIOps）、「10 节点 + 3 组条件边」（建工智库）、「8 节点有向工作流」（自媒体创作）、「7 节点状态机」（医保 Text2SQL）
- **HITL 是高频词**：batch 1 里 4 个项目、batch 3 里 4 个项目都有。实现方式统一是 `interrupt` 挂起 → 人工审批 → `Command(resume)` 恢复
- **checkpoint 断点恢复**：MemorySaver / Checkpointer，强调「长任务断点恢复成功率 100%」（法务平台）

### 类型 D：MCP / A2A 协议层（主类约 3 个，但含金量高）

**形态**：把能力抽成 MCP Server，上层业务只写编排层。

**写得最完整的**（批次 6 P3 与批次 3 第 7 项，实为同一类项目的两份描述）：
- 4 个独立 MCP Server：LLM 调用 / RAG 检索 / 会话记忆 / Prompt 管理
- StreamableHTTP 传输，暴露标准化 Tool / Prompt 原语
- REST—MCP 协议：把外部 HTTP 请求翻译成 MCP 格式
- 四层中间件：认证 → 日志 → 额度 → 路由，每请求一个 TracedID
- 多租户：按 project_id 分 VikingDB Collection 做物理隔离；记忆按 project_id + session_id 隔离，画像按 user_id 跨项目共享
- Serverless 部署：Docker 独立镜像 → 阿里云函数计算 / SAE，按依赖拓扑分层发布，SIGTERM 优雅终止

**A2A 只出现两次**（AIOps 平台、某技术文章），都是「把平台整体打包成一个 A2A Agent，外部系统经标准协议调用」。**这是目前简历里最稀缺的词**。

### 类型 E：NL2SQL / 数据分析 Agent（主类约 5 个）

**形态**：自然语言 → 语义层 / Schema 检索 → SQL 生成 → 校验 → 执行 → 图表 → 解读。

**共性的工程点**：
- **语义层兜底**：YAML 配置指标公式，已覆盖的指标走确定性 SQL 拼装，**零 LLM 调用、零幻觉**；长尾才走 LLM（两个不同简历都写了这个思路，说明是成熟范式）
- **Schema Linking 双路**：Milvus 向量检索定位表 + Neo4j Schema 图沿外键边扩展关联表（医保 Text2SQL）
- **SQL 三级校验**：语法 → 字段存在性（交叉比对 Prompt 注入字段，拦幻觉字段）→ 安全白名单（只允许 SELECT/WITH）
- **失败自修复**：校验失败带错误信息回喂大模型重试，最多 2~3 轮；第 2 轮升级提示词加检查清单
- 准确率普遍在 75%~89%（有测试集的项目）

### 类型 F：记忆与上下文工程（作为横切能力，几乎每个项目都有）

**分层方式高度统一**：
- 短期：Redis 滑动窗口 + 文本摘要压缩
- 长期：向量库存用户画像 / 事实，按 distance 阈值过滤
- 会话：按 session_id / conversation_id 隔离
- 进阶：Mem0 三层记忆（User / Session / Agent），或自研四类记忆（情节 / 语义 / 程序 / 事实）

**效果口径**：Token 消耗降低 30%+、上下文腐烂问题、跨会话用户偏好持久化。

## 五、从简历反推：什么叫「合格的项目」

把上面六类形态和指标口径合起来，一个能写进简历的项目必须同时满足五条：

### 1. 有一个真实的、能说清痛点的业务场景
不需要热门。简历里的场景包括：割草机控制、养老院护理、卤味连锁客服、医美客户转化、集装箱物流、出版社编校。**场景越具体越可信**。

### 2. Agent 是「编排放进状态图」的，不是「prompt 串一下」
判据：能不能说清**几个节点、几条边、在哪一步分叉、失败怎么回退**。
写得好的简历都会直接给数字：15 节点 22 边、10 节点 3 组条件边、7 节点状态机。

### 3. 有至少一项「工程硬东西」
从这批简历里挑，稀缺度从高到低：
- **A2A 协议互操作**（最稀缺）
- **MCP Server 化 + 多租户 + 配额计量**（第二稀缺）
- **沙箱执行 + 权限隔离**
- **interrupt / checkpoint 断点恢复 + 人工审批门禁**
- **父子分块 + 三级缓存 + 幂等锁**
- **RRF 多路融合 + Reranker 精排**
- **RAGAS 双层评估 + CI 回归**

选项目时，看它**自带了上面哪几样**。一个项目如果能覆盖后四项，就已经超过这批简历的中位数。

### 4. 有可复现的评估结果
不要「效果显著」。要「在 N 条测试集上，X 从 A 提到 B」。
即使是你二创后补的评测，也比没有强——**这批简历里三分之二都没有，你有就是优势**。

### 5. 前端 / 交互能讲
你是前端出身，这是差异点。这批简历里只有极少数写了前端：
- 多 Agent 创作平台：AG-UI、Vercel AI SDK Data Stream Protocol、自定义组件渲染事件流
- 商家经营助手：React/TS 流式事件协议 + 任务状态机 + 确认卡片 + taskId 状态快照
- 智库检索平台 / 部门任务：前端只是配角

**大多数 Agent 简历的前端是空白的**，或者只有 Streamlit。你能做「流式事件协议 + 任务状态可视化 + HITL 审批卡片」这一套，是明显的加分项。

## 七、下一步：拿这套标准去筛 GitHub 项目

上面第五节列的五条判据，就是我接下来筛项目的尺子。具体会按这几个方向找：

1. **能承载 LangGraph 状态图的业务型 Agent**（不是框架、不是 SDK）
2. **自带 MCP Server 或 A2A 的实现**
3. **有 HITL / interrupt / checkpoint 的**
4. **带评测集（RAGAS / LLM-as-Judge）的**
5. **有前端交互层的**（你能发挥的地方）
6. **仍活跃维护的**（近半年有提交）

筛选结果另出一份清单，标注每个项目**命中了上面哪几条**、以及**二创切入点**。
